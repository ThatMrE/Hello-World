# Audio-reactive visuals force one licence decision

**The central finding is a trade-off, not a tool: every browser visualiser route that can actually read your audio is either AGPL-3.0 copyleft or something you write yourself, and the one "licence-free" way to use Strudel — iframe-embedding hosted strudel.cc — gives your page zero audio access.** Strudel is `AGPL-3.0-or-later`, verified in the repository `LICENSE` and in every `@strudel/*` package's npm metadata ([tidalcycles/strudel LICENSE](https://raw.githubusercontent.com/tidalcycles/strudel/main/LICENSE); [npm @strudel/repl](https://registry.npmjs.org/@strudel/repl/latest)); Hydra is AGPL-3.0 in both the editor and `hydra-synth` ([hydra-synth LICENSE](https://raw.githubusercontent.com/hydra-synth/hydra-synth/main/LICENSE)); and audioMotion-analyzer, the most polished spectrum analyser in the ecosystem, is `AGPL-3.0-or-later` ([audioMotion-analyzer LICENSE](https://raw.githubusercontent.com/hvianna/audioMotion-analyzer/master/LICENSE)). Strudel's own docs state the consequence plainly: "Distributing a website that includes Strudel generally means sharing the whole application's source under the same or a compatible license" ([Strudel docs, Project Start](https://strudel.cc/technical-manual/project-start/)). Replacing Strudel with **Tone.js (MIT, UMD CDN build, `Tone.Analyser` built in)** is the only way to get full audio reactivity with no copyleft obligation ([npm tone](https://registry.npmjs.org/tone/latest)). Separately, the Bandcamp embed is settled as unanalysable for four independent reasons, so every reactive visual on this site must be driven by audio the page itself generates — and the sharpest architecture available is to connect that synthesis graph to an analyser *only*, never to `ctx.destination`, producing a tempo-locked but inaudible signal that drives visuals without competing with the album. Among desktop tools, TouchDesigner and Jitter have no browser runtime at all and reduce to pre-rendered video; RNBO does export WebAssembly that runs on Netlify with no build step, but it is audio-only and contributes nothing visual.

## The Bandcamp embed is a dead end, and four independent mechanisms close it

This is not a limitation to work around; it is four separate walls, any one of which is sufficient. **First, same-origin policy on the frame**: the embed is served from a Bandcamp origin, and a document cannot read or script a cross-origin child frame's DOM, so there is no `<audio>` element to find and no API that hands you a `MediaStream` or `AudioNode` from inside it. **Second, no cross-document channel**: `postMessage` requires the embedded page to implement a protocol, and Bandcamp's does not — developer reports converge that the embedded player exposes no JavaScript API to play, pause, seek or detect track end, unlike YouTube or SoundCloud ([Parachord issue #1231](https://github.com/Parachord/parachord/issues/1231); [Squarespace forum](https://forum.squarespace.com/topic/328184-question-how-to-prevent-multiple-bandcamp-tracks-from-playing-at-once/)). The Parachord desktop integration resorts to **polling playback state every 500 ms from Electron's privileged main process**, which is not a web-page capability ([Parachord PR #1233](https://github.com/Parachord/parachord/pull/1233)). Bandcamp's published API is no help either: it covers only the Account, Sales Report and Merch Orders APIs for "labels and merchandise fulfillment partners" — no audio, no playback, no streaming ([Bandcamp developer](https://bandcamp.com/developer)). **Third, CORS tainting as a backstop**: even if you somehow obtained a media element pointed at a Bandcamp stream, `createMediaElementSource` on a non-same-origin resource outputs zeroes. Firefox's shipped console error reads "The HTMLMediaElement passed to createMediaElementSource has a cross-origin resource, the node will output silence"; Chrome's reads "MediaElementAudioSource outputs zeroes due to CORS access restrictions" ([Mozilla bug 937718](https://bugzilla.mozilla.org/show_bug.cgi?id=937718); [wavesurfer.js issue #2014](https://github.com/katspaugh/wavesurfer.js/issues/2014)). The rule was deliberate from the start — a 2013 Web Audio WG discussion proposed that `MediaElementAudioSourceNode` "convert data coming from a non-same origin stream to silence" ([W3C public-audio](https://lists.w3.org/Archives/Public/public-audio/2013JulSep/0224.html)), and the mute is total: the element itself stops producing sound. **Fourth, audio graphs do not cross origins at all**: an `AudioContext` belongs to a document, and the iframe's audio reaches the OS mixer, not your graph.

The practical corollary is stronger than "no spectrum bars from the album." You cannot even build *"detect that the Bandcamp player started so I can pause my visualiser"* — there is no event to listen for. A visitor pressing play inside the embed also gives your page's `AudioContext` **no user activation**, because the gesture happens in another origin, so your audio still needs its own click. And no counter-evidence exists: the research found **no documented case of any musician's site reacting to an embedded third-party player** (Bandcamp, Spotify or SoundCloud), which is consistent with the impossibility rather than independent proof of it. Self-hosting your own masters or excerpts on Netlify sidesteps all of this, because same-origin files never trigger the tainting rule in the first place — a 90-second Opus excerpt runs under ~1.5 MB, and `crossOrigin` plus `Access-Control-Allow-Origin` are only needed for *cross*-origin resources.

## Strudel buys Tidal's pattern language and bills you in AGPL

The licence facts are unambiguous and were read from source, not from blog posts. The repository `LICENSE` is the verbatim GNU Affero General Public License v3 ([raw LICENSE](https://raw.githubusercontent.com/tidalcycles/strudel/main/LICENSE)); every package checked reports `"license": "AGPL-3.0-or-later"`, including `@strudel/core` 1.2.6, `@strudel/repl` 1.3.0, `@strudel/web` 1.3.0, `@strudel/draw`, `@strudel/hydra`, `@strudel/embed` and the underlying `superdough` 1.3.0 ([npm registry](https://registry.npmjs.org/@strudel/repl/latest)); and per-file headers repeat the notice inline ([@strudel/webaudio index.mjs](https://cdn.jsdelivr.net/npm/@strudel/webaudio@1.3.0/index.mjs)). The licence survived the project's move from GitHub to Codeberg (`codeberg.org/uzu/strudel`), with the archived GitHub repo labelled "MOVED TO CODEBERG."

Four of Strudel's five documented integration routes are buildless plain HTML, which means the constraint that kills everything else — no npm, no bundler — does *not* kill Strudel ([Strudel docs, Project Start](https://strudel.cc/technical-manual/project-start/)). The decisive axis is instead whether the code runs **in your page** or **in an iframe**:

| Route | Buildless | Audio readable by your page | Licence obligation on your site |
|---|---|---|---|
| `<iframe src="https://strudel.cc/#…">` hand-written | Yes | **No** — cross-origin document | **None** |
| `@strudel/embed` → `<strudel-repl>` | Yes | **No** — loads strudel.cc in an iframe | You serve one AGPL file (`embed.js`) |
| `@strudel/repl` → `<strudel-editor>` | Yes (`main: dist/index.js`) | **Yes** — in-page, `.editor` exposed | AGPL-3.0-or-later |
| `@strudel/web` → `initStrudel()` | Yes (`main: dist/index.js`) | **Yes** — same page, same AudioContext | AGPL-3.0-or-later |
| individual `@strudel/*` packages | **No** — ESM only, no `unpkg` field | n/a | AGPL-3.0-or-later |
| `tone` (MIT) | Yes — npm `unpkg: build/Tone.js` | **Yes** — `Tone.Analyser` | **None** (attribution only) |

The reasoning behind the obligation column is licence-text analysis, not a maintainer ruling or case law, and should be read as such. Loading `@strudel/web` from unpkg into your own page is still conveying Strudel to your users over a network; a CDN is a delivery mechanism, not a licence firewall, and AGPL §13 is triggered by users interacting with the program remotely. Framing hosted strudel.cc is categorically different: the visitor's browser fetches and runs Strudel from the Strudel project's own server under the project's own obligations, and framing an AGPL web app has never been held to make the framing page a derivative work. **No Strudel maintainer statement addresses framing**; their licence note addresses *including* Strudel, which is why this is an inference. For a hand-written vanilla site with no secrets, AGPL compliance is genuinely cheap — a public Git repo plus a visible licence notice discharges it, and the source is effectively readable anyway. The real incompatibility arises only if the site's source must stay proprietary.

Two further Strudel findings change what you would build. **`analyze` is a per-voice wet send, not a master-bus tap.** The pattern controls exist (`export const { analyze } = registerControl('analyze');` and `fft` for FFT size, in [@strudel/core controls.mjs](https://cdn.jsdelivr.net/npm/@strudel/core@1.2.6/controls.mjs)), and `getAnalyserById()` creates real `AnalyserNode`s read back via `getAnalyzerData('time'|'frequency', id)`. But the per-event chain wires the analyser with `effectSend(post, analyserNode, 1)`, and the line that would have connected the master destination to the analyser is **commented out in source**: `// getDestination().connect(analyserNode);` ([superdough superdough.mjs](https://cdn.jsdelivr.net/npm/superdough@1.3.0/superdough.mjs)). So `analysers[1]` hears only events that actually carry `.analyze(1)`. For a whole-mix visual you must either append `.analyze(1)` to every pattern (or `all(x => x.analyze(1))`), or inject your own analyser on `getAudioContext()`, which `superdough` exposes alongside a `setAudioContext(ctx)` setter that lets you own the graph if you call it before anything triggers lazy creation. Convenient shortcut: `.scope()`, `.fscope()` and `.spectrum()` all call `this.analyze(id)` internally, so using one guarantees the send exists and your own custom visual can then read the same analyser. Note also that `@strudel/core`'s default `fft: 8` resolves to `fftSize = 2**(8+5) = 8192`, while `getAnalyserById`'s own default is 1024.

**Strudel's drawing layer is reusable outside the REPL, and composites behind HTML for free.** `getDrawContext()` looks for a canvas with `id="test-canvas"` and, failing that, creates one styled `pointer-events:none; position:fixed; top:0; left:0; width:100%; height:100%` and `document.body.prepend()`s it ([@strudel/draw draw.mjs](https://cdn.jsdelivr.net/npm/@strudel/draw@1.2.6/draw.mjs)) — so if you place `<canvas id="test-canvas">` yourself, Strudel draws into *your* canvas, behind your content, stealing no clicks. The unprefixed visuals (`pianoroll`, `punchcard`, `scope`, `fscope`, `spectrum`, `spiral`, `pitchwheel`) target that canvas; the `_`-prefixed inline variants are a CodeMirror feature and only make sense inside `<strudel-editor>` or strudel.cc ([Strudel docs, Visual Feedback](https://strudel.cc/learn/visual-feedback/)).

Hydra adds no new licence problem on top of Strudel — AGPL plus AGPL combines fine — and `hydra-synth` is the strongest buildless visual engine in this space: a browserified UMD bundle exposing a global `Hydra`, with a `canvas` constructor option so you supply your own element and z-index it behind your HTML ([hydra-synth README](https://github.com/hydra-synth/hydra-synth)). One caveat matters for a public band page: Hydra's `detectAudio` is **microphone** capture via Meyda, and its own README recommends setting it to `false` "to avoid asking for microphone." The clean route is to run Hydra standalone and feed its parameters as thunks (`osc(10, 0, () => bassLevel * 4)`) from analyser values you already have — no mic prompt, no Meyda. Whether Strudel's `initHydra({detectAudio:true})` taps Strudel's own output bus rather than the mic is **unverified and is the key open question** on that route. Pin CDN paths explicitly: `hydra-synth`'s npm `main` points at raw ESM source, and only the `unpkg` field points at `dist/hydra-synth.js`.

## Ecosystem by ecosystem: three categories, and most desktop tools collapse into video

The honest taxonomy is not "browser vs desktop" but **runs in the browser and reads your audio / runs in the browser and cannot read your audio / does not run in the browser at all.**

**d3.js (ISC, [d3/d3 LICENSE](https://raw.githubusercontent.com/d3/d3/main/LICENSE), current 7.9.2) is the wrong renderer and the right mapper.** Its own docs recommend CDN use with no build step, both as an ES module bundle and as a UMD global ([d3js.org/getting-started](https://d3js.org/getting-started)). But SVG performance "can drop sharply once the DOM holds more than about 1,000 elements, which makes Canvas the better choice" ([*D3.js in Action* 3e, ch.15](https://livebook.manning.com/book/d3js-in-action-third-edition/chapter-15)), and one published benchmark measured D3/SVG at **682 ms versus 173 ms for D3/Canvas** on 10,000 rows ([The Linux Code](https://thelinuxcode.com/unleash-the-speed-a-deep-dive-into-d3-js-and-html5-canvas/)). Those are static-render figures, so they *understate* the cost of re-joining 1,024 FFT bins sixty times a second; no benchmark exists that measures precisely that, so the practical ceiling — comfortable to roughly 64–256 mutating SVG elements per frame, canvas required beyond a few hundred — is engineering judgement supported by static benchmarks rather than a measured 60 fps figure. The idiomatic move is to keep `scaleBand`, `scaleLog`, `arc`, `lineRadial`, `curveBasisClosed` and `d3.timer`, and render with `d3.line().context(ctx)` into a 2D canvas. Audio-reactive d3 is a thin, dated niche: the retrievable material is a handful of Observable notebooks and three or four blog tutorials, and **no Observable licence could be verified** because observablehq.com is behind a Vercel bot checkpoint that returned HTTP 429. Observable's default is effectively proprietary — staff describe an opt-in licence list and note that "forks inherit the license and copyright notice of their parents," while a community member characterises the ToS grant as applying "only... on Observable" ([talk.observablehq.com](https://talk.observablehq.com/t/notebook-licenses/3608); [copyright thread](https://talk.observablehq.com/t/copyright-and-software-licenses/364)). Treat every notebook, and every CodePen pen, as all-rights-reserved reference reading. **No CodePen licences were verified either.**

**p5.js and p5.sound are LGPL-2.1, and the p5 audio tutorial corpus is targeting a dead API.** Both licences are verified ([p5.js license.txt](https://raw.githubusercontent.com/processing/p5.js/dev-2.0/license.txt); [npm p5.sound](https://registry.npmjs.org/p5.sound)). Loading them from jsDelivr as separate unmodified `<script>` files is dynamic linking in the plainest sense, so nothing obliges the site's own source to be LGPL — but that is a reasoned application of LGPL-2.1 §6, not a quotation, and the Processing Foundation publishes no licensing FAQ addressing CDN use. The consequential finding is the rewrite: **p5.sound is no longer bundled with p5.js**, has been rebuilt as "a minimal abstraction of the Tone.js library," and the copy inside the Complete Library download "is an outdated version incompatible with p5.js 2.x" ([p5js.org/download](https://p5js.org/download/); [processing/p5.sound.js](https://github.com/processing/p5.sound.js)). You need two pinned tags, p5 first: `p5@2.4.0/lib/p5.min.js` then `p5.sound@0.4.2/dist/p5.sound.min.js`. And the analysis API has shrunk drastically: `p5.FFT` exposes only `analyze()` and `waveform()`; the constructor's `fftSize` "must be a power of two between **16 and 1024**" with a default of **32**; `analyze()` returns amplitudes **0 to 1** rather than 0–255 (realistically clustered in 0–0.1, as p5's own example's `map(spectrum[i], 0, 0.1, …)` concedes); and `getEnergy()`, `getCentroid()` and `linAverages()` **return zero occurrences in a grep of the full 797 KB 0.4.2 bundle** ([p5.sound 0.4.2 bundle](https://cdn.jsdelivr.net/npm/p5.sound@0.4.2/dist/p5.sound.js); [p5.FFT reference](https://p5js.org/reference/p5.sound/p5.FFT/)). Legacy p5.sound gave 1024 bins at 0–255 plus named bands `bass [20,140]`, `lowMid [140,400]`, `mid [400,2600]`, `highMid [2600,5200]`, `treble [5200,14000]` ([v1 p5.FFT](https://v1.p5js.org/reference/p5.sound/p5.FFT/)). So essentially every p5 audio visualiser tutorial written before ~2024 — The Coding Train's FFT track, the 2018 Codrops roundup — will not run. Replacing the lost helpers is arithmetic (`binFreq(i) = i * sampleRate / (2 * size)`; centroid `Σ(f·m)/Σm`), but the cheaper move for this project is to skip `p5.FFT` entirely, build a plain `AnalyserNode` on the audio library's context, and let p5 be purely a drawing library. Note also the official p5.js examples are **CC BY-NC-SA 4.0** and OpenProcessing's default is **CC BY-NC-SA** — NonCommercial and ShareAlike, so read them and write your own ([p5js.org example](https://p5js.org/examples/Sound-Connecting-To-ToneJS/); [OpenProcessing help](https://intercom.help/openprocessing/en/articles/5714786-choosing-a-license-for-your-sketches)). The Java-Processing-to-web question is settled and closed: Processing.js was **archived 5 December 2018** at v1.6.6 ([processing-js](https://github.com/processing-js/processing-js)), IDE JavaScript Mode was "moved out of the Processing IDE" after 2.0 beta 8 ([javascript-mode-processing](https://github.com/fjenett/javascript-mode-processing)), and Processing 4's only export is "a Java application as an executable file" ([processing.org/environment](https://processing.org/environment/)).

**TouchDesigner has no browser runtime, and the free tier cannot even encode the web's default codec.** Derivative ships no WASM build, no web player and no web export; the only "web TD player" discussion is an **unanswered community wish-list thread** with no staff reply ([Derivative forum](https://forum.derivative.ca/t/a-web-td-player-treejs-based/991083)). TouchEngine is a Windows/macOS SDK that loads `.tox` files and requires a paid local install ([Derivative, TouchEngine](https://derivative.ca/UserGuide/TouchEngine)). Web Server DAT, WebSocket DAT, WebRTC and NDI are all *live* mechanisms requiring a running TouchDesigner process — and WebRTC additionally "cannot be established without a signaling server," plus a TURN relay where STUN fails ([Derivative, WebRTC](https://derivative.ca/UserGuide/WebRTC)). That leaves pre-rendered media, where the free Non-Commercial tier is capped at **1280×1280** and "Encoding movies in H.264/H.265/AV1 codec is only available with a Commercial or Pro license," making **VP8/VP9 in WebM** the unrestricted route ([Derivative, Download](https://derivative.ca/download); [Movie File Out TOP](https://derivative.ca/UserGuide/Movie_File_Out_TOP)). This is good news for delivery, because autoplay blocking "is *not* applied to `<video>` elements when the source media does not have an audio track," so `autoplay muted loop playsinline` on a silent loop just works ([MDN Autoplay guide](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Autoplay)). A loop is a texture, not a reactive visual — but it can be *made* to read as reactive by driving `opacity`, `filter: brightness()/contrast()/hue-rotate()`, `transform: scale()` or the opacity of 2–4 stacked loops from analyser bands, and compositing a truly reactive canvas layer over it with `mix-blend-mode: screen`. `playbackRate` is the weakest lever: browsers mute outside roughly 0.5–4 ([MDN playbackRate](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Audio_and_video_delivery/WebAudio_playbackRate_explained)), and a Firefox-44-era bug report describes analyser-plus-playbackRate degrading playback ([Bugzilla 1251640](https://bugzilla.mozilla.org/show_bug.cgi?id=1251640)) — current Firefox behaviour unverified. Two honest holes here: **no verified real-world examples were found of musicians, labels or studios shipping TouchDesigner visuals as web video**, and Derivative's licence pages **never address publishing Non-Commercial output on a website**, so whether a monetised band site clears their compensation-based test is a question for Derivative's support, not something to assert.

**Max/MSP reaches the web only through RNBO, and RNBO is audio-only.** Jitter has no web export; Max's `jweb`/`jit.web` objects run Chromium *inside* Max, the opposite direction ([Cycling '74, Web Browser and jweb](https://docs.cycling74.com/userguide/web_browser/)). Node for Max "controls a local Node.js process from Max" with "no access to Max's internal API for patcher scripting or graphics" — a local helper, not a delivery path ([node.script](https://docs.cycling74.com/reference/node.script)). RNBO's Web Export, by contrast, is a genuine fit for the stated constraints: a remote cloud compiler produces **a single `.json` file** containing "everything you need to run your patch in the browser," loaded by `@rnbo/js` as an **AudioWorkletNode**, with the docs naming Netlify and GitHub Pages explicitly ([RNBO, The Web Export Target](https://rnbo.cycling74.com/learn/the-web-export-target); [Using the Web Page Template](https://rnbo.cycling74.com/learn/using-the-web-page-template)). The compiler is involved only at export time, so there is no runtime dependency beyond the CDN. Because the device is an AudioWorkletNode, it sits in the same graph as your `AnalyserNode` — so RNBO can be the audio *source* a visualiser reads. But every export target is audio ("embedding a **sound engine** in a website," VST3/AU, Raspberry Pi, Max for Live, C++): there is no graphics, Jitter or WebGL target ([Cycling '74, Introducing RNBO](https://cycling74.com/products/rnbo)). Cost is the obstacle: RNBO is **$299 permanent / $100 per year / $10 per month** and "requires a Max 8 or Max 9 license" ([Cycling '74 shop](https://cycling74.com/shop/rnbo)), so the real entry price is a Max licence *plus* RNBO — the widely repeated "bundled with Max" story is wrong. Also **the RNBO EULA could not be read** (the licensing vignette URL 404s; support pages returned 403), so the report cannot assert that there are no restrictions on publishing exported web code — although "embedding a sound engine in a website" is plainly the marketed use. Real deployments exist but are demos rather than named artist sites: Cycling '74's own `rnbo.example.webpage` template, and community projects `stretta/Juno2` and `maceq687/FaceArp` ([RNBO, JavaScript Webpage Template](https://rnbo.cycling74.com/explore/javascript-webpage-template); [stretta/Juno2](https://github.com/stretta/Juno2)).

**The remaining browser-native pool sorts cleanly by whether it will accept a node your page owns.** Only **butterchurn**, **audioMotion-analyzer** and **clubber.js** are documented to take an external node — butterchurn via `visualizer.connectAudio(audioNode)` ([jberg/butterchurn](https://github.com/jberg/butterchurn)), audioMotion via a `source` option and `connectInput()` accepting "an HTMLMediaElement or an AudioNode (or any of its descendants)" plus an `audioCtx` option ([hvianna/audioMotion-analyzer](https://github.com/hvianna/audioMotion-analyzer)). **wavesurfer.js** (BSD-3-Clause, and the most actively maintained at 8.1.1 published 2026-11-24), **Wave.js** (MIT, 24.8 KB) and **Vudio.js** all insist on owning the audio via URL, `<audio>` element or `MediaStream` ([wavesurfer.js](https://github.com/katspaugh/wavesurfer.js); [foobar404/Wave.js](https://github.com/foobar404/Wave.js)). **Vanta.js** is MIT and pretty but has no audio reactivity at all — mouse, touch and gyroscope only — and credits its Clouds effects to Shadertoy shaders, which is a licence question in itself ([tengbao/vanta](https://github.com/tengbao/vanta)). **three.js is MIT** and its `webaudio_visualizer.html` example is ~150 lines teaching the one pattern most worth stealing: a one-row R8 audio texture, `new THREE.DataTexture(analyser.data, fftSize/2, 1, THREE.RedFormat)`, refreshed per frame and sampled in the fragment shader as `texture2D(tAudioData, vec2(vUv.x, 0.0)).r` ([three.js example source](https://raw.githubusercontent.com/mrdoob/three.js/dev/examples/webaudio_visualizer.html)). That is a mini-Shadertoy audio channel, which brings us to the licence trap there: **a Shadertoy shader with no stated licence falls under CC BY-NC-SA 3.0 Unported**, non-commercial and share-alike, and "most of shaders don't change it" ([shadertoy.com/terms](https://www.shadertoy.com/terms); [Ogre forums](https://forums.ogre3d.org/viewtopic.php?t=96906)) — **but shadertoy.com returned HTTP 403 to every direct fetch and served a Cloudflare interstitial to curl, so that wording comes from a search engine's extraction of the terms page plus corroborating secondary sources and must be re-read directly before anyone relies on it.** The good news is that you don't need their code: Shadertoy's audio channel is a **512×2 single-channel 8-bit texture**, row 0 spectrum and row 1 waveform, built from `fftSize = 2048`, Blackman window, smoothing **0.8**, clamped to **−100…−30 dB** — which are exactly the Web Audio `AnalyserNode` defaults, so `getByteFrequencyData()` already produces row 0 (first 512 of 1024 bins) and `getByteTimeDomainData()` row 1 ([soulthreads gist](https://gist.github.com/soulthreads/2efe50da4be1fb5f7ab60ff14ca434b8), citing the [Web Audio FFT spec](https://webaudio.github.io/web-audio-api/#fft-windowing-and-smoothing-over-time)). Write your own GLSL against that convention and you get Shadertoy ergonomics with zero licence exposure. **Flag explicitly as unsafe to copy**: `azeem/webvs`, `mfcc64/html5-showcqtbar`, `preziotte/partymode` and `mdn/voice-change-o-matic` have **no LICENSE file** on `main` or `master`; `Vudio.js` has an outright conflict, with npm declaring MIT while the upstream repo contains no LICENSE at all; and `osci-render` is GPL-3.0. Among permissive drop-ins, the standout is **butterchurn + butterchurnPresetsMinimal (MIT, 188 KB + 187 KB, UMD globals)**, whose two caveats are that the README documents only `pnpm add` and never mentions CDN use (the UMD global was confirmed by reading the published bundle bytes), and that npm has not republished it since **2019-03-12** (presets since 2018-06-09). For Gibber, Glicol and Tone.js, only Tone.js survives scrutiny: Gibber is MIT but shows `version: 0.0.1`, no discoverable recent core releases and a sibling `gibberish` repo with no LICENSE; Glicol is MIT but has no analyser or visual story and no UMD field. **No repository commit dates could be verified at all** — `api.github.com` was blocked for this session, so npm publish dates were used throughout as an activity proxy.

**The AnalyserNode itself is the whole API surface**, and the cheapest licence in the catalogue: MDN's oscilloscope and frequency-bar `draw()` functions are ~25–35 lines each and **CC0 public domain, "No licensing notice is necessary"** ([MDN attribution and licensing](https://developer.mozilla.org/en-US/docs/MDN/Writing_guidelines/Attrib_copyright_license); [Visualizations with Web Audio API](https://developer.mozilla.org/en-US/docs/Web/API/Web_Audio_API/Visualizations_with_Web_Audio_API)). They are not runnable as-is — they reference undefined externals and use `// ...` placeholders — so budget ~20 lines of setup around them, after which you own the code outright.

## Plumbing: one context, one gesture, one analyser, and a hard DPR cap

The analyser is safe to graft onto a graph another library built, because MDN states the pass-through property outright: "You don't need to connect the analyser's output to another node for it to work, as long as the input is connected to the source, either directly or via another node." So the non-destructive recipe is `libraryOutputNode.connect(myAnalyser)` and leave `myAnalyser` unconnected — audio still reaches the speakers by the library's existing path, and your analyser is a parallel branch. Prefer the library's own accessor over rewiring: Strudel exposes `getAudioContext()` and `setAudioContext()` from `superdough`; Tone.js exposes `Tone.getContext().rawContext` for the native context and `Tone.getDestination().connect(analyser)` for a tap above its managed master chain ([Tone.js Context typings](https://app.unpkg.com/tone@15.0.4/files/build/esm/core/context/Context.d.ts); [Tone.js Analyser docs](https://tonejs.github.io/docs/15.1.22/classes/Analyser.html)); and p5.sound documents context sharing as a **first-class feature**, with `setAudioContext(ctx)` reassigning its module-level context and handing it to Tone's `setContext`, plus an official example, "Connecting to ToneJS," built around exactly this ([p5js.org example](https://p5js.org/examples/Sound-Connecting-To-ToneJS/)). **Ordering is the whole game**: `setAudioContext` only reassigns the module-level reference, and Web Audio nodes cannot be connected across contexts, so nodes already built on the old context are stranded. Call it once, before any `new p5.FFT(...)` or `loadSound(...)`, and before anything triggers Strudel's lazy `getAudioContext()`. Mixing libraries requires **one** AudioContext: two contexts means two clocks, two autoplay-unlock states and no shared analyser.

Every route needs a gesture. Strudel's own README states it plainly — "Due to the Autoplay policy, you can only play audio in a browser after a click event" — and ships `initAudioOnFirstClick` for it ([@strudel/web README](https://cdn.jsdelivr.net/npm/@strudel/web@1.3.0/README.md)). Create the context lazily inside the handler, check `ctx.state !== "running"` and `await ctx.resume()`, keep the button visible so a rejected resume degrades to "click again," and re-check state on `visibilitychange` because iOS can drop a context into `"interrupted"` after a call or backgrounding. `navigator.getAutoplayPolicy("audiocontext")` reports `"allowed"`, `"allowed-muted"` or `"disallowed"` if you want to branch ([MDN Autoplay guide](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Autoplay)).

For self-hosted audio, the CORS story is almost a non-story on this stack: Netlify serves your own files from your own origin, so tainting never arises and no `Access-Control-Allow-Origin` header is needed. If you ever do serve audio from another origin, set `crossOrigin = 'anonymous'` **before the element loads** *and* send a matching header — reports note the attribute is required even when the server already sends `Access-Control-Allow-Origin: *` ([wavesurfer.js issue #2014](https://github.com/katspaugh/wavesurfer.js/issues/2014)).

Mobile performance is dominated by pixels, not shapes. A full-bleed canvas at 400×800 CSS px on a 3× DPR phone is 2.88 million pixels to fill every frame, and MDN's own advice is "have a smaller canvas and scale up rather than a bigger canvas and scale down" ([MDN Optimizing canvas](https://developer.mozilla.org/en-US/docs/Web/API/Canvas_API/Tutorial/Optimizing_canvas)). Capping DPR at 1.5–2 buys more than every micro-optimisation combined. The rest of MDN's list reads like a checklist for this exact genre: "Avoid the `shadowBlur` property whenever possible," avoid floating-point coordinates, avoid text, use `getContext("2d", { alpha: false })` when you don't need transparency, batch into one `beginPath()`/`fill()` and "draw a polyline instead of multiple separate lines." The glow effect audio visualisers want should come from a half-resolution offscreen canvas upscaled, or CSS `filter: blur()` on a lower stacked canvas — not from `shadowBlur` per shape. Allocate the typed array once outside the loop (MDN's own example hoists it; its per-bar template-literal colour is the one thing *not* to copy). Never call `getImageData` per frame. On a 120 Hz phone, rAF fires at 120 Hz, so cap your own update rate explicitly — a background visual at 30 fps halves energy use and is usually indistinguishable. And pause on **three** independent signals: `visibilitychange` (do it yourself, since Firefox still ticks background rAF at roughly 1 Hz, which would leave you running a 1 Hz strobe), `IntersectionObserver` for scroll-out, and the user's own control — calling `cancelAnimationFrame` rather than early-returning inside the callback. Canvas 2D with a DPR cap and a two-canvas layer split is the right default here; a single WebGL fullscreen quad with an inline GLSL string is the escalation path and needs no bundler either.

## Three flashes per second is the invariant that makes accessibility cheap

**Adopt "never more than three flashes in any one second" as a hard design invariant and you satisfy both WCAG 2.3.1 (Level A) and 2.3.2 (Level AAA) at once, and need no analysis tooling.** SC 2.3.1 requires that "Web pages do not contain anything that flashes more than three times in any one second period," or that the flash stays below the general and red flash thresholds, and its own Understanding document notes that "no tool is necessary to evaluate for this condition if flashing is less than or equal to 3 flashes in any one second" ([W3C Understanding SC 2.3.1](https://www.w3.org/WAI/WCAG22/Understanding/three-flashes-or-below-threshold.html)). SC 2.3.2 removes the escape hatches entirely: 2.3.1 "permits flashing if it is dim enough or covers a small enough area," whereas 2.3.2 "prohibits any flashing above three times per second, regardless of brightness or size, so even a single flashing pixel is a violation" ([W3C Understanding SC 2.3.2](https://www.w3.org/WAI/WCAG22/Understanding/three-flashes.html)). Three design consequences follow directly from the definitions. A "general flash" requires "a pair of opposing changes in relative luminance of 10% or more of the maximum relative luminance (1.0)… where the relative luminance of the darker image is below 0.80" — so **fast motion inside a ≤10% luminance window is not a flash by definition**, which makes a tight palette the cheapest route to fast, safe visuals. A "red flash" is "any pair of opposing transitions involving a saturated red" and is tested **independently of luminance**, so no rapid saturated-red transitions at all; MDN's warning that #990000 being "websafe" "does *not* mean it is 'safe for not causing seizures'" closes the dark-red loophole ([MDN Seizure disorders](https://developer.mozilla.org/en-US/docs/Web/Accessibility/Guides/Seizure_disorders)). And the small-area exemption — "no more than a total of .006 steradians within any 10 degree visual field," estimated as a 341 × 256 px rectangle, i.e. 87,296 CSS pixels — **can never apply to a full-bleed background visual**, only to a small inline widget.

The pause obligation applies to this site specifically. SC 2.2.2 bites when moving content "(1) starts automatically, (2) lasts more than five seconds… and (3) is presented in parallel with other content," and WCAG counts a start "as a result of an indirect interaction" as automatic — so launching the visualiser as a side-effect of your play button still counts. Because the page carries a tracklist, links and a Bandcamp embed, condition (3) is met, and the "essential" exemption is defined too narrowly to help ("if removed, would fundamentally change the information or functionality") — a decorative visual behind an album page plainly fails that test ([W3C Understanding SC 2.2.2](https://www.w3.org/WAI/WCAG22/Understanding/pause-stop-hide.html)). So: a persistent, keyboard-reachable pause control, visible without hovering, remembered in `localStorage`. Note the structural irony — a dedicated full-screen visualiser route with no other content would escape 2.2.2, which is exactly why the Awwwards one-offs never needed a pause button and a real musician's site does.

Photosensitivity guidance pushes in the same direction and adds one thing WCAG does not: **autostart off, with a specific warning.** MDN quotes the Epilepsy Foundation of America consensus — "A flash is a potential hazard if it has luminance ≥20 cd/m2, occurs at a frequency of ≥3 Hz, and occupies a solid visual angle of ≥0.006 steradians" — and notes that "flashing lights between the frequencies of five to 30 flashes per second (Hertz) are most likely to trigger seizures," while warning that "for some people… flashing/blinking can cause symptoms at less than 3 Hz." Its instruction is explicit: make flashing content "turned off when the viewer first encounters it, and that a user must opt-in," and "Describe the animation that is to follow" rather than using a generic label ([MDN Seizure disorders](https://developer.mozilla.org/en-US/docs/Web/Accessibility/Guides/Seizure_disorders)). That opt-in gate is free, because autoplay policy requires a click anyway — design one "Enter / Play" screen that starts the audio, starts the visuals, and carries the notice.

For `prefers-reduced-motion`, the sanctioned pattern is **substitute, not delete**: MDN's own example replaces a scaling `pulse` with an opacity-only `dissolve`, "a more muted animation that is not a vestibular motion trigger," and notes that "scaling or panning large objects can be vestibular motion triggers" ([MDN prefers-reduced-motion](https://developer.mozilla.org/en-US/docs/Web/CSS/@media/prefers-reduced-motion)). Keep a visual that still answers to the music through opacity and colour density with `smoothingTimeConstant` near 0.9, no translation or scaling. Because the canvas is drawn in JS, honour the preference in JS too, via `matchMedia("(prefers-reduced-motion: reduce)")` plus a `change` listener so live OS changes take effect — the MDN page documents only the CSS form, so the JS equivalent is standard practice rather than a quotation. Three switches should exist and compose: the OS preference, the on-page control, and the automatic hidden/offscreen pause. Finally, the audit habit most likely to catch an accidental violation: **a visualiser that fully clears to black each frame and then draws bright shapes is producing large opposing luminance changes many times per second** even though no code says "flash." Use a translucent clear (`rgba(0,0,0,0.08)`) for trails, and clamp the brightness response so a loud transient cannot swing the canvas from near-black to near-white.

## Prior art: the famous artists shipped apps, and the useful web examples are two open repos

The reputations mislead. When major artists wanted reactive, sensor-driven or generative experiences they shipped **apps**: Massive Attack's *Fantom* (2016) remixes *Ritual Spirit* in real time from heartbeat, location, time and movement ([Wikipedia: Ritual Spirit](https://en.wikipedia.org/wiki/Ritual_Spirit)); Radiohead's *PolyFauna* (2014) came out of the *King of Limbs* sessions with Universal Everything; Eno and Chilvers' *Bloom* (2008) hands over to "a generative music player" when idle ([Soundfly](https://flypaper.soundfly.com/discovery/artists-pioneering-musical-mobile-apps/)). Aphex Twin's interactive Weirdcore work is **AR and live visuals, not a website** — Warp's WAPP480 app, built with Tokyo studio KALKUL, unlocks four track-by-track AR experiences by scanning the vinyl insert ([Warp: WAPP480](https://warp.net/wapp480); [weirdcore.tv](https://weirdcore.tv/av-portfolio/)). The useful corollary: **there is no convention that a musician's homepage must be audio-reactive.** Doing it is a differentiator, not catching up.

Two web examples are documented at the code level and worth actually reading. **`mattdesl/audiograph.xyz`** was Pilotpriest's *TRANS* album site — "a visual exploration of Pilotpriest's 2016 album TRANS," using "WebGL, WebAudio and Dolby Digital Plus," Awwwards Site of the Day on 20 May 2016 with a developer score of 8.33/10, and its source is public: Three.js plus `three-effectcomposer`, `three-simplicial-complex`, and notably `web-audio-player`, a library that exists precisely to abstract the `<audio>`-versus-decoded-buffer choice and the mobile unlock dance ([Awwwards: Audiograph](https://www.awwwards.com/sites/audiograph); [repo metadata](https://repos.ecosyste.ms/hosts/GitHub/repositories/mattdesl%2Faudiograph.xyz)). Its architectural lesson is exactly this brief's constraint restated: **the page owned the audio it visualised**, which is why there is no embed in it. **`ryanachten/IndiOfficial`** is the closer match to a vanilla no-build target — an open-source New Zealand artist site where the music generates the visuals using Web Audio and the **Canvas** API rather than WebGL, with FFT sampling driving generative "colonies" inspired by Chladni and Lissajous figures ([IndiOfficial](https://github.com/ryanachten/IndiOfficial)). Beyond those, **ARKx's Codrops write-up for Coala Music** (Dec 2023) is the best tutorial-grade document on synchronising "audio frequencies and tempo… to drive procedural particle animations" in Three.js, though **Codrops returned HTTP 403 to automated fetching, so its technical details here rest on a search summary**; and Active Theory's Bon Iver *"i"* visualiser was Awwwards SOTD on 11 June 2020 ([Codrops](https://tympanus.net/codrops/2023/12/19/creating-audio-reactive-visuals-with-dynamic-particles-in-three-js/); [Awwwards music + WebGL](https://www.awwwards.com/websites/?category=music-sound&technology=webgl)). For effort calibration, the two ends are documented: Nekologic's in-house audio-reactive web visualiser case study reports **four person-months** for bespoke shader work ([Nekologic](https://neko-logic.com/works/audio-reactive-web-visualiser/)), while a canvas-2D spectrum piece with a DPR cap, a reduced-motion path and a pause control is a day or two. The gap is almost entirely shader authoring and art direction; the Web Audio plumbing is the small part.

## Shortlist: six candidates for this exact setup

Effort figures are rough estimates calibrated against the prior art above, assuming someone comfortable with vanilla JS, and counting working-and-accessible rather than art-directed.

| # | Candidate | Licence | Est. effort | Audio reactive |
|---|---|---|---|---|
| 1 | **Tone.js + hand-written Canvas 2D** (MDN CC0 recipes, optional d3 scales) | **MIT** + CC0 + ISC | 1–2 days | Yes |
| 2 | **`@strudel/web` + your own canvas**, site relicensed | **AGPL-3.0-or-later** | 0.5–1 day | Yes |
| 3 | **butterchurn + presets, fed from Tone.js** | **MIT** (both) | 1 day + a test | Yes |
| 4 | **`<strudel-editor>` (`@strudel/repl`)**, Hydra bundled | **AGPL-3.0-or-later** | 1–2 hours | Yes |
| 5 | **Own WebGL quad on Shadertoy's 512×2 texture convention** | **Yours** (MIT/none) | 2–4 days | Yes |
| 6 | **Pre-rendered loop + AnalyserNode-driven CSS/blend layer** | Your render + CC0 glue | 1 day (plus render time) | Reads as reactive |

**1. Tone.js plus hand-written Canvas 2D — the no-copyleft default.** Two CDN tags (`tone@15.1.22/build/Tone.js` via npm's `unpkg` field, giving the `Tone` global) and about 60 lines: `const analyser = new Tone.Analyser('fft', 1024)`, `Tone.getDestination().connect(analyser)`, then MDN's CC0 bar or oscilloscope `draw()` adapted into a radial form with `d3-scale`/`d3-shape` on a canvas if you want clean log-frequency mapping. On the page this looks like a single full-bleed canvas prepended behind your content at `z-index: -1`, drawing a slow radial spectrum or a thick oscilloscope line in two or three album colours inside a ≤10% luminance window, with a translucent trail clear. The cost is real: Tone.js gives you a synthesis framework, not Tidal's pattern language, so you hand-write the sequencing instead of writing `n("<0 1 2 3>*8")`. **This is the recommendation if the site's source must stay unencumbered.**

**2. `@strudel/web` plus your own canvas — the pattern-language option, at the price of AGPL.** One pinned tag (`unpkg.com/@strudel/web@1.3.0`), `initStrudel()`, your own play/stop buttons, patterns carrying `.analyze(1)`, and a rAF loop reading `getAnalyzerData('frequency', 1)`. Optionally add pinned `hydra-synth@1.4.0/dist/hydra-synth.js` rendering into a canvas you own, with its parameters fed as thunks from those analyser values — no mic prompt. On the page: a Strudel-generated bed (or a silent one, see below) behind a `<canvas id="test-canvas">` you place yourself so Strudel's own `scope`/`spectrum`/`pianoroll` composite behind your HTML for free, or a Hydra feedback field washing under the tracklist. **You must publish the site's source under AGPL-3.0-or-later with a visible repo link.** Two things to verify in a browser console first, both flagged as unverified in the research: whether `initStrudel()` actually puts `getAnalyzerData`, `analysers` and `setAudioContext` on `window`, and that your pinned `hydra-synth` URL serves the UMD bundle rather than raw ESM source.

**3. butterchurn plus `butterchurnPresetsMinimal`, fed from Tone.js — maximum visual impact per hour.** Two script tags, ~375 KB, MIT on both, UMD globals `window.butterchurn` and `window.butterchurnPresets`, and a WebGL 2 reimplementation of Milkdrop 2 — swirling, feedback-warped, bloom-heavy fullscreen plasma fields. On the page this is a hero: a full-bleed Milkdrop field behind a minimal tracklist, cycling presets per track. Three caveats, stated honestly: the README documents only `pnpm add` and never mentions CDN usage, so expect to write ~15 lines of glue yourself; npm has not republished the library since **2019** or the presets since **2018**, which is a driver-regression risk rather than a functional blocker; and **whether `connectAudio()` accepts an `AnalyserNode` specifically is untested and undocumented** — butterchurn runs its own internal FFT, so the correct input is most likely a source or gain node, which is an inference to confirm empirically before committing. Flashing discipline matters more here than anywhere else on this list, since Milkdrop presets were authored for a desktop media player with no accessibility constraints: cap the brightness response and keep a pause control.

**4. `<strudel-editor>` — the two-line "it just works" option.** `<script src="https://unpkg.com/@strudel/repl@1.3.0">` plus a `<strudel-editor>` element with the pattern in an HTML comment gets you the full REPL running in-page (not an iframe), mini-notation highlighting, the inline `._scope()` / `._pianoroll()` / `._spectrum()` visuals, and **Hydra already bundled** (the published files include a `dist/hydra-C4R5I71T.js` chunk). The `.editor` property exposes the StrudelMirror instance for `setCode`, `start`, `stop` and `evaluate` from your own buttons. On the page this reads as a live-codeable panel — a "play with the record" section where a visitor can edit the pattern — which is a genuinely distinctive thing for a compilation site to offer. Costs: you inherit the REPL's visual design, the `_`-prefixed visuals only work inside it, **no attribute list beyond `code` is documented** (so making the editor unobtrusive or visuals-only is unverified), and it is AGPL.

**5. Your own WebGL fullscreen quad on Shadertoy's audio-texture convention — the licence-clean shader route.** A single quad plus an inline GLSL string needs no bundler. Upload a 512×2 R8 texture per frame: `getByteFrequencyData()` into row 0 (first 512 of 1024 bins) and `getByteTimeDomainData()` into row 1, which reproduces Shadertoy's channel essentially byte-for-byte because its constants *are* the Web Audio defaults. Unmodified Shadertoy audio shaders will then run — but **do not ship them**: the default is CC BY-NC-SA 3.0, non-commercial and share-alike, and per-shader licences have changed over time. Write your own shader against the convention, borrow three.js's MIT `DataTexture` pattern for reference, and you own the result outright. On the page: a tunnel, plasma or kaleidoscopic field at full resolution with real per-pixel reactivity, which is the only route on this list that scales to 3× DPR without compromise. Highest effort, highest ceiling.

**6. Pre-rendered loop plus an analyser-driven CSS and blend layer — the TouchDesigner-compatible hybrid.** If the aesthetic you want lives in TouchDesigner, this is the only static-site path: render a short seamless loop (6–12 s, WebM/VP9 on the free tier, MP4/H.264 as a second `<source>`), ship it `autoplay muted loop playsinline` so autoplay blocking does not apply, then make it *read* as reactive by stacking 2–4 loops and driving each one's opacity from a different frequency band, and compositing a genuinely reactive canvas layer over the top with `mix-blend-mode: screen`. The analyser must read your synthesis or your self-hosted preview, never the silent video. On the page: a cinematic, art-directed texture that breathes with the audio — honest-looking, because the canvas layer really is reactive. Constraints to accept: the free Non-Commercial tier caps at 1280×1280 and cannot encode H.264, seamless looping is a render-time problem with **no Derivative documentation found on authoring technique**, and whether a monetised site clears Derivative's compensation-based licence test is unresolved in their published wording.

**Three routes deliberately excluded.** An `<iframe src="https://strudel.cc/#…">` with a hash-encoded pattern carries no licence obligation and is genuinely zero-risk — but it is as opaque as the Bandcamp embed, so it defeats the purpose unless you want a purely decorative live-coding curio (use the long hash URL, not the short share link, which the docs say "depend[s] on a database that may not be permanent"). **audioMotion-analyzer** is the best-engineered analyser here, takes an external node, ships 4.5.4 as of 2026-01-09, and is **AGPL-3.0-or-later** — include it only if you have already accepted candidate 2's copyleft, in which case it is a strict upgrade on hand-rolled bars. And **RNBO** is worth the money only if the site needs genuinely interactive or generative *audio* beyond what Strudel or Tone.js give free; it contributes no visuals, costs a Max licence plus $299 (or $10/month), and its EULA could not be read.

**The architecture note that applies to every candidate above.** A Bandcamp embed and a reactive audio layer both making sound means two uncontrollable sources, and you cannot detect the embed's state to duck it. The sharpest resolution is to **connect the synthesis graph to the analyser only — never to `ctx.destination`.** You get a real, structured, tempo-locked signal driving the visuals, with no sound at all, no competition with the album, and no risk of a visitor hearing two things at once. The visuals move musically because they are reading a musical source; the record plays uninterrupted in the embed. The only cost is still needing one gesture to start the AudioContext, which you need anyway for the accessibility opt-in. If you want visitors to hear the generative layer, make it mutually exclusive with the album in the UI — an "idle / intro" mode that the visible act of pressing play replaces, with one unambiguous "now playing" indicator. And whatever you ship, do not imply the visuals read the album stream: "generative visual — press play on the album below to listen" is accurate, and avoids the mismatch a visitor notices within seconds when the bars do not match the beat.

## Where this evidence is thin

Several findings rest on secondary sources or on reasoning from licence text, and should not be treated as settled. **Shadertoy's terms could not be fetched** — `/terms`, `/faq` and `/howto` all returned 403, curl got a Cloudflare interstitial, and web.archive.org was blocked by egress policy — so the CC BY-NC-SA 3.0 default comes from a search engine's extraction plus corroborating forum sources and must be re-read before anyone relies on it legally. The 512×2 audio-texture layout has **no official Shadertoy documentation**; it comes from a community gist and one third-party tool's docs. **No repository commit dates were verified anywhere in this research**, because `api.github.com` was unavailable for the session; npm publish dates stand in as an activity proxy throughout. **No Observable notebook licence and no CodePen licence was verified** (observablehq.com returned 429 behind a bot checkpoint; CodePen's default reuse policy was not checked), so treat all of that code as all-rights-reserved reference. **butterchurn's acceptance of an `AnalyserNode` specifically is untested**, and the inference is that it wants a source or gain node instead. **RNBO's EULA could not be read** (404 on the licensing vignette, 403 on support), so no claim is made about restrictions on publishing exported web code. **No verified examples were found of musicians shipping TouchDesigner visuals as web video**, despite the technique obviously being widespread — a genuine hole, not a conclusion that none exist. Additionally: Strudel's licence implications for framing rest on AGPL §13's text rather than a maintainer ruling; the LGPL-and-CDN analysis for p5.js is reasoned from §6 with no Processing Foundation statement available; Derivative publishes no sentence permitting or forbidding web publication of Non-Commercial output; Bandcamp's Terms of Use were not read, so the self-hosting conclusion rests on the artist's ownership premise; the normative Web Audio spec text for `AnalyserNode` defaults could not be quoted (read values off a live node instead); Codrops and Awwwards both blocked automated fetching; whether Strudel's `initHydra({detectAudio:true})` taps Strudel's output rather than the microphone is unverified; and the SVG-versus-canvas and mobile element-count thresholds are engineering judgement from non-audio benchmarks.

## Conclusion

The question "what is the best in-browser music visualiser" turns out to be the wrong frame for this site, because the browser-visualiser ecosystem has already answered it: almost nothing is a library you install. The permissive, maintained, node-accepting options number about **three** (butterchurn, clubber.js, and MDN's CC0 recipes), while the richest tools in the space — Strudel, Hydra, audioMotion-analyzer — are all AGPL, and the richest *visual* traditions, Shadertoy and OpenProcessing, are gated behind NonCommercial share-alike defaults that a Bandcamp-linked site should not quietly ignore. The real decision is therefore a licence posture chosen up front, and it has exactly two sane resolutions: accept AGPL and publish the site's source (cheap, since the site is hand-written vanilla HTML with nothing to hide, and it buys Tidal's pattern language plus Hydra plus the best analyser in the field), or stay on MIT with Tone.js and write the visuals yourself from CC0 and MIT patterns. Trying to have both by iframing strudel.cc buys silence.

The second insight is subtler and more useful: the Bandcamp constraint, read properly, is a creative brief rather than a loss. Because the page cannot react to the record, it must either generate its own music or fake it — and the strongest answer is neither of the obvious ones. Running a synthesis graph into an analyser with no path to `ctx.destination` produces a visual that is genuinely reactive to a genuinely musical signal, costs no bandwidth, raises no CORS question, competes with nothing, and needs no audio permission beyond the gesture that accessibility guidance demands anyway. That is a better artefact than a spectrum analyser bolted to a stream would have been, and it is the one configuration in this entire space where the technical constraint, the licensing constraint, the autoplay constraint and the photosensitivity constraint all point the same way.
