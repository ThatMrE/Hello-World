# Integration, accessibility and design prior art for audio-reactive visuals on a static musician's site

Scope note: researched late November 2026. Target stack assumed throughout: static vanilla HTML/CSS/JS, no build step, Netlify hosting (all assets same-origin), Bandcamp embed for commerce/playback, Strudel.cc / in-browser synthesis as the analysed signal.

## Web Audio plumbing: the canonical AnalyserNode pattern

### Takeaway
`AnalyserNode` is the whole API surface you need: create it, set `fftSize`, allocate one typed array, and re-fill that array once per animation frame. It is an inline node that passes audio through unchanged and also works with its output unconnected, which is exactly what makes it safe to graft onto a graph some other library built.

### Cited Findings
- `fftSize` is "an unsigned long value representing the size of the FFT (Fast Fourier Transform) to be used to determine the frequency domain" — [MDN AnalyserNode](https://developer.mozilla.org/en-US/docs/Web/API/AnalyserNode)
- `frequencyBinCount` is "an unsigned long value half that of the FFT size. This generally equates to the number of data values you will have to play with for the visualization" — [MDN AnalyserNode](https://developer.mozilla.org/en-US/docs/Web/API/AnalyserNode)
- `minDecibels` is "a double value representing the minimum power value in the scaling range for the FFT analysis data, for conversion to unsigned byte values — basically, this specifies the minimum value for the range of results when using `getByteFrequencyData()`"; `maxDecibels` is the corresponding maximum — [MDN AnalyserNode](https://developer.mozilla.org/en-US/docs/Web/API/AnalyserNode)
- `smoothingTimeConstant` is "a double value representing the averaging constant with the last analysis frame — basically, it makes the transition between values over time smoother" — [MDN AnalyserNode](https://developer.mozilla.org/en-US/docs/Web/API/AnalyserNode)
- The four read methods: `getFloatFrequencyData(array)` "copies the current frequency data into a `Float32Array`"; `getByteFrequencyData(array)` "copies the current frequency data into a `Uint8Array` (unsigned byte array)"; `getFloatTimeDomainData(array)` "copies the current waveform, or time-domain, data into a `Float32Array`"; `getByteTimeDomainData(array)` "copies the current waveform, or time-domain, data into a `Uint8Array`". All copy into an array you pass in; none returns a new array — [MDN AnalyserNode](https://developer.mozilla.org/en-US/docs/Web/API/AnalyserNode)
- IMPORTANT SOURCING CAVEAT: the MDN AnalyserNode page does **not** state default values or ranges. The widely-cited defaults (`fftSize` 2048, power of two 32–32768; `minDecibels` -100; `maxDecibels` -30; `smoothingTimeConstant` 0.8, range 0–1) come from the Web Audio spec, which I was unable to quote directly (see Gaps). MDN's own example code does set `analyser.fftSize = 2048;` and comments `analyser.frequencyBinCount` as `// 1024`, which corroborates the 2048 default and the halving relationship — [MDN AnalyserNode](https://developer.mozilla.org/en-US/docs/Web/API/AnalyserNode)
- Canonical graph insertion from MDN's visualisation guide: `source.connect(analyser); analyser.connect(distortion); distortion.connect(audioCtx.destination);` — i.e. the analyser sits inline between source and destination — [MDN Visualizations with Web Audio API](https://developer.mozilla.org/en-US/docs/Web/API/Web_Audio_API/Visualizations_with_Web_Audio_API)
- Pass-through / tap behaviour, quoted: "You don't need to connect the analyser's output to another node for it to work, as long as the input is connected to the source, either directly or via another node." — [MDN Visualizations with Web Audio API](https://developer.mozilla.org/en-US/docs/Web/API/Web_Audio_API/Visualizations_with_Web_Audio_API)
- Typical values MDN itself uses: `fftSize = 2048` for the oscilloscope/waveform example ("captures more samples for a smooth line"); `fftSize = 256` for the frequency bar graph, because a smaller size "makes each bar wide enough to look like a bar instead of a thin strand" — [MDN Visualizations with Web Audio API](https://developer.mozilla.org/en-US/docs/Web/API/Web_Audio_API/Visualizations_with_Web_Audio_API)
- MDN's bar-graph example multiplies bar width by 2.5 "because most of the bins are empty for typical sounds" — a direct admission that a linear FFT bin layout wastes most of its width on inaudible top octaves — [MDN Visualizations with Web Audio API](https://developer.mozilla.org/en-US/docs/Web/API/Web_Audio_API/Visualizations_with_Web_Audio_API)
- Waveform draw loop (abridged from MDN): allocate `dataArray = new Uint8Array(analyser.frequencyBinCount)` once, then per frame `requestAnimationFrame(draw); analyser.getByteTimeDomainData(dataArray);` and map each sample with `const v = dataArray[i] / 128.0; const y = v * (HEIGHT / 2);` — [MDN Visualizations with Web Audio API](https://developer.mozilla.org/en-US/docs/Web/API/Web_Audio_API/Visualizations_with_Web_Audio_API)
- Frequency draw loop: `analyser.getByteFrequencyData(dataArray)` then `barHeight = dataArray[i] / 2` with `barWidth = (WIDTH / bufferLength) * 2.5` — [MDN Visualizations with Web Audio API](https://developer.mozilla.org/en-US/docs/Web/API/Web_Audio_API/Visualizations_with_Web_Audio_API)
- MDN says to use `requestAnimationFrame()` rather than `setInterval()` for canvas animation — [MDN Optimizing canvas](https://developer.mozilla.org/en-US/docs/Web/API/Canvas_API/Tutorial/Optimizing_canvas)

### Inferences
- Practical division of labour: `getByteTimeDomainData` → oscilloscope/Lissajous/waveform shapes (0–255 centred on 128, so subtract 128 and divide by 128 for a −1..1 signal). `getByteFrequencyData` → bars, radial spectra, anything where you want values already normalised into 0–255 against `minDecibels`/`maxDecibels`. `getFloatFrequencyData` → when you want true dBFS numbers for thresholding, beat detection or your own scaling, because the byte version has already clamped and quantised the dynamic range.
- `minDecibels`/`maxDecibels` only matter to the *byte* frequency method. For a musical spectrum, widening the window (e.g. `minDecibels = -90`, `maxDecibels = -10`) makes quiet passages visible; narrowing it (e.g. -70 to -25) makes the visualiser look more "punchy" because more of the 0–255 range is spent on the loud band. This is the single most effective aesthetic knob and it costs nothing at runtime.
- `smoothingTimeConstant` near 0 gives twitchy, frame-accurate response (good for percussive material); near 0.9 gives slow, gluey motion (good for pads/drone and kinder to photosensitive viewers, see accessibility section). It is applied by the node, so it is free compared with smoothing in JS.
- For a musical rather than engineering spectrum, use a larger `fftSize` (2048–4096) and then *group the linear bins into log-spaced bands yourself* (e.g. 24–48 bands). MDN's own 2.5× bar-width hack is evidence that the raw linear layout is visually wrong for music.
- Allocate the typed array once outside the loop. MDN's phrasing ("they do not return new arrays, so you must allocate the array before calling them") makes this explicit, and it matters because per-frame allocation is a documented jank source (see Performance).

### Gaps
- I could not quote the normative Web Audio spec text for AnalyserNode defaults/ranges. The spec page (`webaudio.github.io/web-audio-api/`) is ~400k characters and WebFetch could not reach the relevant section within its windowing; the W3C TR copy has the same problem. Treat the defaults above as spec-derived-but-unquoted. Anyone implementing should read values back off a live node (`new AnalyserNode(ctx).fftSize`) rather than trust a secondary source.

## Inserting an AnalyserNode into a graph another library already built

### Takeaway
Because the analyser needs only an input connection and alters nothing, you never have to rewire a foreign library's graph destructively — you tap whatever node you can get a handle on, usually the library's destination/output. Tone.js and p5.sound both expose their context and output explicitly; Strudel exposes `getAudioContext()` and has a built-in `.analyze()` mechanism that already creates AnalyserNodes for you.

### Cited Findings
- The analyser works as a pure tap: "You don't need to connect the analyser's output to another node for it to work, as long as the input is connected to the source, either directly or via another node." — [MDN Visualizations with Web Audio API](https://developer.mozilla.org/en-US/docs/Web/API/Web_Audio_API/Visualizations_with_Web_Audio_API)
- **Strudel**: the `@strudel/webaudio` package (v1.1.0) exports `initAudioOnFirstClick`, `getAudioContext` and `webaudioOutput` — so the same `AudioContext` Strudel's output uses is directly reachable — [@strudel/webaudio README on unpkg](https://app.unpkg.com/@strudel/webaudio@1.1.0/files/README.md)
- **Strudel**: its own technical manual on custom sounds uses `getAudioContext()` to create nodes on the context Strudel's output uses — [Strudel technical manual: Sounds](https://strudel.cc/technical-manual/sounds/)
- **Strudel**: a Tidal Club thread reports that Strudel's `.analyze(id)` pattern method creates a Web Audio `AnalyserNode` stored in an `analysers[id]` map, which you can read from your own `requestAnimationFrame` loop; the thread points at `tscope` in `scope.mjs` as the reference implementation and says the `fft` function sets the analyser's `fftSize` — [Strudel audio reactive, get values from audio output (Tidal Club)](https://club.tidalcycles.org/t/strudel-audio-reactive-get-values-from-audio-output/5413). Caveat: the thread is roughly two years old; verify the names against current Strudel source.
- **Strudel, third-party corroboration**: an unofficial Strudel MCP server exposes an AnalyserNode attached to Strudel's audio graph with `fft_size` and `smoothing` settings; and the `vibe-soundlab` project routes Strudel's output through its own analyser-based mixer/EQ/visualiser per channel — both are community code, not official docs — [strudel-mcp-server](https://github.com/williamzujkowski/strudel-mcp-server); [vibe-soundlab PR #10](https://github.com/FionaPreroll/vibe-soundlab/pull/10)
- **Tone.js**: `Tone.getContext()` returns Tone's `Context` wrapper, and `Context` exposes a `rawContext` getter described as the unwrapped `AudioContext` or `OfflineAudioContext` — so `Tone.getContext().rawContext` gives the native context — [Tone.js Context typings](https://app.unpkg.com/tone@15.0.4/files/build/esm/core/context/Context.d.ts)
- **Tone.js** also ships its own wrapper: `Tone.Analyser` is "a wrapper around the native Web Audio's AnalyserNode" that "extracts FFT or Waveform data from the incoming signal", constructed with type `"fft"` or `"waveform"`; `getValue()` calls `getFloatFrequencyData` for `"fft"` and `getFloatTimeDomainData` for `"waveform"` — [Tone.js Analyser docs 15.0.4](https://tonejs.github.io/docs/15.0.4/classes/Analyser.html)
- **Tone.js** size ranges differ by version: older docs give 32–32768 (default 1024), 14.x/15.x docs give 16–16384 — check your pinned version — [Tone.js Analyser r13](https://tonejs.github.io/docs/r13/Analyser); [Tone.js Analyser 15.0.4](https://tonejs.github.io/docs/15.0.4/classes/Analyser.html)
- `BaseAudioContext.createAnalyser()` is the factory for a node "that can be used to expose audio time and frequency data and create data visualizations" — [MDN createAnalyser()](https://developer.mozilla.org/en-US/docs/Web/API/BaseAudioContext/createAnalyser)

### Inferences
- The general recipe, in order of preference:
  1. **Use the library's own analyser if it has one.** Strudel `.analyze(id)` + `fft(n)`; Tone `new Tone.Analyser("fft", 1024)` connected from `Tone.getDestination()`. Fewest moving parts, survives library upgrades.
  2. **Tap the library's output node.** `libraryOutputNode.connect(myAnalyser)` and leave `myAnalyser` unconnected. Audio still reaches the speakers via the library's existing path; your analyser is a parallel branch. This is the non-destructive pattern and is what the MDN quote licenses.
  3. **Insert between output and destination** (`output.disconnect(); output.connect(analyser); analyser.connect(ctx.destination);`) only if you cannot get a tap point. This is destructive-ish and can be undone by the library re-wiring itself.
- For Tone.js specifically, prefer `Tone.getDestination().connect(analyser)` over inserting before `ctx.destination`, because Tone manages its own master chain (volume/limiter) and re-wiring under it is where upgrades break.
- For p5.sound, `getAudioContext()` is the documented accessor for the shared context (p5.sound also ships `p5.FFT`/`p5.Amplitude` wrappers which are themselves AnalyserNode-based). I did not independently verify current p5.sound 2.x API names in this pass — see Gaps.
- Mixing libraries requires **one** AudioContext. If Strudel created the context, get it via `getAudioContext()` and hand it to anything else rather than letting a second library construct its own; two contexts means two clocks, two autoplay-unlock states and no shared analyser.

### Gaps
- I did not find a first-party p5.sound page in this pass confirming `getAudioContext()` in the current (p5.js 2.x / p5.sound standalone) release. The function is long-standing in p5.sound and is also the name Strudel uses, but treat the p5 specifics as unverified here.
- No official Strudel documentation page for `.analyze()` was located; the evidence is a Tidal Club forum thread plus community code. Verify against current Strudel source before building on it.

## Autoplay policy and the click-to-start requirement

### Takeaway
You cannot start audio or an AudioContext without a user gesture in any current major browser; the universal fix is to create *and* resume the context inside a click/tap handler and keep a visible play button. iOS Safari adds an `interrupted` state you must handle on return from backgrounding.

### Cited Findings
- Web Audio is in scope for autoplay blocking: "a website or app can start playing audio using the `start()` method on a source node linked to the `AudioContext`. Doing so outside the context of handling a user input event is subject to autoplay rules." — [MDN Autoplay guide](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Autoplay)
- The general rule: autoplay with audio is allowed only if the audio is muted, the user has interacted with the site, the site is allowlisted, or an iframe has been granted the `autoplay` Permissions Policy — [MDN Autoplay guide](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Autoplay)
- **Firefox**: the preference `media.autoplay.block-webaudio` (default `true`) blocks Web Audio until the page has had *sticky activation*; set to `false`, Web Audio is always allowed to autoplay — [MDN Autoplay guide](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Autoplay)
- You can query policy at runtime: `navigator.getAutoplayPolicy("audiocontext")` (or pass a specific context) returns `"allowed"`, `"allowed-muted"` or `"disallowed"`; MDN recommends checking on page load because there is no event for policy changes — [MDN Autoplay guide](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Autoplay)
- **Strudel** ships a helper named `initAudioOnFirstClick` in `@strudel/webaudio`, i.e. the click-to-unlock pattern is baked into the library's public API — [@strudel/webaudio README](https://app.unpkg.com/@strudel/webaudio@1.1.0/files/README.md)

### Inferences
- The MDN autoplay guide is thin on the `suspended`/`resume()` mechanics and on Safari/iOS specifics — it links out to the Chrome and WebKit policy posts rather than restating them. So: the *obligation* (gesture required) is well sourced; the *per-browser mechanics* below are widely-known practice rather than quotable from the pages I read (see Gaps).
- Recommended implementation for this site:
  ```js
  let ctx = null;
  startButton.addEventListener("click", async () => {
    ctx ??= new (window.AudioContext || window.webkitAudioContext)();
    if (ctx.state !== "running") await ctx.resume();
    // only now start Strudel / schedule nodes / begin the rAF loop
  });
  ```
  Create lazily inside the gesture, reuse one context, always check `ctx.state`, and keep the button visible so a rejected `resume()` degrades to "user can click again".
- iOS practicality: an `AudioContext` can enter `"interrupted"` after a phone call or backgrounding, so re-check `ctx.state !== "running"` on `visibilitychange` and on the next user gesture, not just once at startup.
- A play gate is not only an autoplay workaround — it doubles as the accessibility opt-in for flashing visuals (see WCAG section). Design one gate that serves both: a single "Enter / Play" screen that starts audio, starts the visualiser, and is where the photosensitivity notice lives.
- Note the asymmetry with the Bandcamp iframe: the embed handles its own gesture inside its own origin, so a visitor pressing play *in the Bandcamp player* does **not** give your page's AudioContext a user activation. If your visuals read your own synthesis, you need your own separate click.

### Gaps
- I did not fetch the Chrome autoplay policy post or the WebKit policy post in this pass, so Chrome's "Media Engagement Index" details and Safari's exact per-element rules are unquoted here.

## Bandcamp embed limits

### Takeaway
The Bandcamp embedded player is a cross-origin iframe with no public JS/postMessage control surface and no documented events; its audio is unreachable by the parent page's Web Audio API for two independent reasons (you cannot reach into the iframe at all, and even same-page cross-origin media routed through `createMediaElementSource` outputs silence). There is no legitimate route to analysing Bandcamp-hosted audio in your page. Self-hosting your own masters on Netlify sidesteps the whole problem because everything is same-origin.

### Cited Findings
- **Official embed path**: Bandcamp's help centre says to click the Share/Embed control beneath the album cover art, then "embed this album", and that you can customise size, colour, tracklist and merch images. No API or event documentation appears — [Bandcamp help: How do I create a Bandcamp embedded player?](https://get.bandcamp.help/hc/en-us/articles/23020711574423-How-do-I-create-a-Bandcamp-embedded-player)
- Bandcamp also documents an "exclusive embed", "a special type of embedded player that a site like Pitchfork, Fader or Stereogum can use" — again no programmatic interface — [Bandcamp help: How do I set up an exclusive embed?](https://get.bandcamp.help/hc/en-us/articles/23020695344791-How-do-I-set-up-an-exclusive-embed)
- **The Bandcamp API is not for this.** Bandcamp's developer page says "Labels and merchandise fulfillment partners can interact with their accounts via the Bandcamp API", access is by registration (email Bandcamp with "a brief description of how you intend to use API access"), and the APIs listed are only the **Account API, Sales Report API and Merch Orders API** plus the OAuth token endpoint `https://bandcamp.com/oauth_token` — i.e. business/fulfilment data, no audio, no playback, no streaming — [Bandcamp developer](https://bandcamp.com/developer)
- **No playback API on the embed**: developer reports converge that Bandcamp's embedded player exposes no JavaScript API to play, pause, seek or detect track end, unlike YouTube or SoundCloud — [Parachord issue #1231](https://github.com/Parachord/parachord/issues/1231); [Squarespace forum: prevent multiple Bandcamp tracks playing at once](https://forum.squarespace.com/topic/328184-question-how-to-prevent-multiple-bandcamp-tracks-from-playing-at-once/)
- **No events, so third parties poll**: the Parachord desktop integration polls playback state every 500 ms from Electron's main process (which can reach cross-origin frames via `webContents.mainFrame.frames` / `WebFrameMain.executeJavaScript`) rather than listening for any Bandcamp event. That is an Electron privilege, not a web-page capability, and not a Bandcamp feature — [Parachord PR #1233](https://github.com/Parachord/parachord/pull/1233)
- **Contrast**: SoundCloud publishes a widget API with postMessage commands and Acast documents a postMessage embed API with play/pause/seek events — so the absence is specific to Bandcamp, not a limitation of iframes — [Acast embed player API](https://learn.acast.com/en/articles/4485460-embed-player-api)
- **oEmbed: conflicting evidence.** Ghost and Drupal maintainers both concluded Bandcamp does not support oEmbed (the Drupal issue was closed "works as designed", with the maintainer calling it "unfortunate that Bandcamp doesn't support oEmbed") — [Ghost forum](https://forum.ghost.org/t/no-support-for-bandcamp-embed-how-can-i-contribute/16955); [Drupal oembed_providers issue #3402361](https://www.drupal.org/project/oembed_providers/issues/3402361). Against that, a third-party WordPress plugin lists `https://bandcamp.com/api/oembed` as its metadata source — [DEL Embed for Bandcamp plugin](https://wordpress.com/plugins/del-embed-for-bandcamp). This endpoint is undocumented by Bandcamp and unverified; even if it works it returns embed HTML/metadata, **not** audio or playback events.
- **Cross-origin media is silenced by Web Audio, by design.** Firefox's console error: "The HTMLMediaElement passed to createMediaElementSource has a cross-origin resource, the node will output silence." Chrome's: "MediaElementAudioSource outputs zeroes due to CORS access restrictions" — [Mozilla bug 937718](https://bugzilla.mozilla.org/show_bug.cgi?id=937718); [wavesurfer.js issue #2014](https://github.com/katspaugh/wavesurfer.js/issues/2014)
- The rule's provenance: a 2013 Web Audio WG discussion proposed that `MediaElementAudioSourceNode` "convert data coming from a non-same origin stream to silence", and a 2014 follow-up that "a cross-origin media element without an accepted crossorigin attribute should be muted" — [W3C public-audio, Jul–Sep 2013](https://lists.w3.org/Archives/Public/public-audio/2013JulSep/0224.html)
- The spec section is titled "Security with MediaElementAudioSourceNode and Cross-Origin Resources"; an open Web Audio issue notes "MediaElementAudioSourceNode outputs zeroes for such media" and that the spec says "the contents of the track might become inaccessible to the current origin due to cross-origin protections" — [WebAudio/web-audio-api issue #2453](https://github.com/WebAudio/web-audio-api/issues/2453)
- **Side effect worth knowing**: once a cross-origin element is routed into the graph, the element itself stops producing sound entirely — the mute is total, not just absent from the analyser — [SO: how to predict or undo failure of createMediaElementSource](https://kaweah.freedombox.rocks/kiwix/stackoverflow.com_en_all_2023-11/questions/73743022/how-to-predict-or-undo-failure-of-createmediaelementsource)
- **The fix for self-hosted audio**: set `crossOrigin` on the element — `crossorigin="anonymous"` in HTML or `audio.crossOrigin = 'anonymous'` in JS — *before* it loads, and serve a matching `Access-Control-Allow-Origin` header. Reports note the attribute is needed even when the server already sends `Access-Control-Allow-Origin: *` — [wavesurfer.js issue #2014](https://github.com/katspaugh/wavesurfer.js/issues/2014); [Mozilla bug 937718](https://bugzilla.mozilla.org/show_bug.cgi?id=937718)
- Historical browser divergence: Mozilla bug 937718 (silence despite `crossOrigin="anonymous"` + `ACAO: *`) was marked fixed in Firefox 37; a WebKit bug reported WebKit being stricter than other browsers and "likely not matching the spec" — [Mozilla bug 937718](https://bugzilla.mozilla.org/show_bug.cgi?id=937718); [WebKit bug 195043](https://bugs.webkit.org/show_bug.cgi?id=195043)

### Inferences
- **Why the Bandcamp embed is doubly impossible**, stated precisely for implementation notes:
  1. *Same-origin policy on the frame.* The embed is served from a Bandcamp origin (`bandcamp.com` / `iframes.bandcamp.com`). A document cannot read or script a cross-origin child frame's DOM, so you cannot find its `<audio>` element, let alone its nodes. There is no API to hand you a `MediaStream` or `AudioNode` from inside it.
  2. *No cross-document channel.* Even the sanctioned cross-origin channel, `postMessage`, requires the *embedded* page to implement a protocol and emit messages. Bandcamp's does not (no documentation, and third-party integrations resort to polling from privileged Electron contexts). So there is nothing to listen to — not even "is it playing".
  3. *Tainting as a backstop.* Suppose you bypassed (1) and (2) and got a media element whose source is a Bandcamp stream URL. `createMediaElementSource` on a non-CORS-same-origin resource outputs zeroes and mutes the element. So even the hypothetical shortcut yields silence.
  4. *Audio graphs don't cross origins at all.* An `AudioContext` belongs to a document. The iframe's audio reaches the OS mixer, not your graph. There is no "capture the page's audio" web API available to a page about itself (tab capture is an extension/`getDisplayMedia` user-consent flow, not something to ship on a band site).
- **Therefore**: do not build any feature that claims to react to the Bandcamp player. Do not even build "detect that the Bandcamp player started so I can pause my visualiser" — there is no event for it.
- **What *is* available**: options, roughly in order of how well they fit a no-build static site.
  - *Self-host a short preview/excerpt* (30–90 s per track, or one 2–4 minute montage) as same-origin files on Netlify. Netlify serves your own files from your own origin, so `MediaElementAudioSourceNode` tainting never arises, no `Access-Control-Allow-Origin` header is needed, and `crossOrigin` is unnecessary (harmless if set). This is the lowest-risk real-audio route and it is also the commercially sensible one: the full album stays behind the Bandcamp embed where it earns.
  - *Self-host the full album.* Technically identical. Rough budget: Opus at 96–128 kbps or AAC at 128 kbps is ~0.7–1.0 MB per minute, so a 40-minute album is roughly 30–50 MB; MP3 at 192 kbps is ~1.4 MB/min, ~55–60 MB. Serve `.opus`/`.webm` with an `.m4a`/`.mp3` fallback via multiple `<source>` elements (Safari historically lags on Opus-in-WebM). Note that this competes with your own Bandcamp page for streams.
  - *In-browser synthesis (Strudel / Tone / WebAudio).* No files, no CORS, no bandwidth, and the analyser signal is perfect because you own every node. This is the option that makes the visuals genuinely reactive at zero network cost.
  - *Microphone input* (`getUserMedia` → `createMediaStreamSource`) so the visuals react to whatever is actually playing, including the Bandcamp embed, via the room. Works, but asks for a mic permission on a band site, which is a trust cost, and is useless on muted/headphone listening. Mention as a novelty, not a default.
  - *Fake it.* Drive the visuals from a pre-analysed data file (offline FFT baked to JSON) synced to a self-hosted preview, or from a deterministic generative system with no audio dependency at all. For a site where the Bandcamp embed does the real playback, a *non-reactive* generative visual that merely looks alive is honest and bulletproof.
- **Licensing/terms in self-hosting your own masters alongside a Bandcamp embed**: if the artist owns the recording and composition (stated premise here), there is no licensing obstacle to hosting excerpts or full files on their own site — Bandcamp's embed is a distribution/retail integration, not an exclusivity grant. Two practical caveats: (a) if any track has a featured performer, sample, or co-writer, their agreement may constrain free distribution; (b) if the release is enrolled in any exclusivity-bearing programme (e.g. a label deal or a "Bandcamp exclusive" window), check that. I found no Bandcamp term in the pages read that forbids self-hosting your own audio elsewhere — but I did not read Bandcamp's full Terms of Use in this pass (see Gaps).

### Gaps
- I did not read Bandcamp's Terms of Use / artist agreement directly, so the licensing point is reasoned from the ownership premise rather than quoted from Bandcamp's terms. Worth a direct read before publishing full-length self-hosted masters.
- The existence and behaviour of `https://bandcamp.com/api/oembed` is unverified and contested; if you want embed metadata programmatically, test it yourself and expect no stability guarantee.
- I could not quote the normative spec text of the cross-origin section directly (page-size limits); the behaviour is nonetheless corroborated by both Firefox's and Chrome's shipped console errors and the WG's own issue tracker.

## Performance: mobile canvas 2D vs WebGL, frame budget, battery, offscreen pausing

### Takeaway
On mobile, the dominant costs are pixel count (canvas size × devicePixelRatio), per-frame allocation, and a handful of expensive 2D features (`shadowBlur`, text, sub-pixel coordinates, readbacks). Canvas 2D is fine for a few hundred simple shapes at an honest DPR cap; WebGL is what you reach for when you want thousands of elements or shader effects. Pause the loop on both `visibilitychange` and `IntersectionObserver`.

### Cited Findings
- MDN's canvas optimisation list, quoted: "Avoid floating point coordinates"; "Sub-pixel rendering occurs when you render objects on a canvas without whole values", and non-integer coordinates "force extra work for anti-aliasing" — round with `Math.floor()` — [MDN Optimizing canvas](https://developer.mozilla.org/en-US/docs/Web/API/Canvas_API/Tutorial/Optimizing_canvas)
- "Avoid the `shadowBlur` property whenever possible"; "Avoid text rendering whenever possible"; "Avoid unnecessary canvas state changes"; "Render screen differences only, not the whole new state"; "draw a polyline instead of multiple separate lines" — [MDN Optimizing canvas](https://developer.mozilla.org/en-US/docs/Web/API/Canvas_API/Tutorial/Optimizing_canvas)
- Turn off transparency when you don't need it: "Set the `alpha` option to `false` when creating a drawing context", which "lets the browser optimize rendering" — `canvas.getContext("2d", { alpha: false })` — [MDN Optimizing canvas](https://developer.mozilla.org/en-US/docs/Web/API/Canvas_API/Tutorial/Optimizing_canvas)
- Scaling: "CSS transforms are faster since they use the GPU. The best case is to not scale the canvas, or have a smaller canvas and scale up rather than a bigger canvas and scale down." — [MDN Optimizing canvas](https://developer.mozilla.org/en-US/docs/Web/API/Canvas_API/Tutorial/Optimizing_canvas)
- High-DPI handling: set backing size to CSS size × `window.devicePixelRatio`, call `ctx.scale(dpr, dpr)`, and set display size via CSS `style.width/height` — [MDN Optimizing canvas](https://developer.mozilla.org/en-US/docs/Web/API/Canvas_API/Tutorial/Optimizing_canvas)
- Other tips: pre-render repeated primitives to an offscreen canvas; don't scale images inside `drawImage` (cache sizes); layer multiple stacked `<canvas>` elements so static content isn't redrawn; put large static backgrounds in CSS on a `<div>` under the canvas; benchmark `clearRect()` vs `fillRect()` vs resizing to clear; "be careful with heavy physics libraries" — [MDN Optimizing canvas](https://developer.mozilla.org/en-US/docs/Web/API/Canvas_API/Tutorial/Optimizing_canvas)
- Backgrounded tabs: MDN's Page Visibility documentation states most browsers stop `requestAnimationFrame` callbacks for background tabs and hidden iframes to improve performance and battery life; Chrome's developer blog states Chrome does not call `requestAnimationFrame()` when a page is in the background, behaviour in place since 2011 — [MDN Using the Page Visibility API](https://developer.mozilla.org/docs/DOM/Using_the_Page_Visibility_API); [Chrome: Background tabs in Chrome 57](https://developer.chrome.com/blog/background_tabs)
- Firefox differs: Mozilla bug threads report Firefox running the refresh driver (including rAF) at a maximum of 1 tick per second for background tabs — [Mozilla bug 1352205](https://bugzilla.mozilla.org/show_bug.cgi?id=1352205); [Mozilla bug 1548561](https://bugzilla.mozilla.org/show_bug.cgi?id=1548561)
- `IntersectionObserver` is orthogonal to tab visibility — it tracks viewport intersection and will not fire for a tab switch; Chrome's guidance uses it for logic tied to an element's actual visual visibility in the viewport — [Mozilla bug 1548561](https://bugzilla.mozilla.org/show_bug.cgi?id=1548561); [Chrome: Efficient background processing](https://developer.chrome.com/docs/modern-web-guidance/guides/performance/efficient-background-processing)
- Chromium shipped rAF throttling based on viewport visibility for cross-origin iframes — relevant because your Bandcamp embed is exactly that — [Intent to implement and ship: throttling requestAnimationFrame callbacks based on viewport visibility](https://groups.google.com/a/chromium.org/g/blink-dev/c/_SRHebxivJs)
- The recommended composite pattern: "combining requestAnimationFrame for the loop itself, IntersectionObserver to pause when the slider scrolls off-screen, visibilitychange for tab switches" — [Polite animation with IntersectionObserver, requestAnimationFrame, and reduced-motion (Umbraco community)](https://community.umbraco.com/docs/tutorials/foundations/intersection-observer-paused-animation/)

### Inferences
- **Frame budget.** At 60 Hz you have 16.7 ms per frame; practical target for JS+draw work is under ~10 ms to leave room for compositing, and under ~8 ms on mid-range Android. On 120 Hz phones a rAF loop will be *called* at 120 Hz (8.3 ms budget), so cap your own update rate explicitly (e.g. skip frames to 60 fps) rather than letting the visualiser consume twice the power on a ProMotion/high-refresh device. For a background/ambient visual, deliberately running at 30 fps halves energy use and is usually indistinguishable.
- **The real mobile killer is pixels, not shapes.** A full-bleed canvas on a 3× DPR phone at 400×800 CSS px is 1200×2400 = 2.88 M pixels to fill every frame. MDN's own advice ("have a smaller canvas and scale up rather than a bigger canvas and scale down") is the mitigation: cap DPR at 1.5–2 (`Math.min(devicePixelRatio, 2)`), or render at 0.5–0.75 scale and upscale with CSS. This one change usually buys more than every micro-optimisation combined.
- **Per-frame allocation** causes GC sawtooth: allocate the analyser's `Uint8Array`/`Float32Array` once, reuse point/particle objects, avoid building strings per shape. The commonest accidental allocation in visualiser code is a template-literal colour per bar (MDN's own example does `` `rgb(${barHeight + 100} 50 50)` `` inside the loop) — hoist to a small precomputed palette array.
- **`fillRect` counts.** A few hundred `fillRect`s per frame is fine; thousands is not, mostly because each is a separate state change plus rasterisation. Batch into a single `beginPath()`/`rect()`.../`fill()` where the fill colour is shared, and follow MDN's "draw a polyline instead of multiple separate lines".
- **`shadowBlur` and `filter: blur()` are the classic trap** for the glowy look that audio visualisers want. MDN says avoid `shadowBlur` outright. Cheaper substitutes: draw to a half-resolution offscreen canvas and upscale (free blur from bilinear filtering); layer two canvases with CSS `filter: blur()` on the lower one (GPU, composited once, not per-shape); or fake persistence with a translucent `fillRect` clear (`rgba(0,0,0,0.08)`) instead of `clearRect` — a trails effect that costs one rect.
- **`getImageData` is a pipeline stall.** It forces a GPU→CPU readback and synchronises the renderer; never call it per frame. MDN's optimisation page doesn't even list it, but the rule stands: if you need feedback effects, keep them on the GPU by `drawImage`-ing the canvas into itself or by using WebGL ping-pong textures.
- **2D vs WebGL, decision rule for this project.** Canvas 2D: no build step, trivially readable code, fine for waveform lines, radial spectra, a few hundred bars/dots, and any "ink and paper" aesthetic. WebGL: needed for >~2000 independent elements, per-pixel shader effects, feedback/trails at full resolution, or anything you want to stay smooth at 3× DPR. Given the stated constraint (static site, no build step, vanilla JS), **Canvas 2D with a DPR cap and a 2-canvas layer split is the right default**, with a raw-WebGL fullscreen-quad fragment shader as the escalation path if a shader look is wanted (a single quad + GLSL string needs no bundler either).
- **Battery/thermal.** A continuously animating full-screen canvas is a sustained GPU+CPU load; on phones this shows up as warmth and throttling within minutes, which then *looks* like your code got slower. Mitigations that matter: cap DPR, cap fps, stop entirely when offscreen or hidden, and honour `prefers-reduced-motion` (which correlates with users who have battery-saver and reduced-animation system settings on).
- **Pause on three signals, not one**: `document.visibilitychange` (tab switch — and do it explicitly rather than relying on the browser, since Firefox still ticks at ~1 Hz and you don't want a 1 Hz strobe), `IntersectionObserver` (scrolled out of view), and the user's own pause control (required by WCAG 2.2.2, below). Also `cancelAnimationFrame` on pause rather than an early-return inside the callback, so the loop genuinely stops.
- Because Chromium throttles rAF in cross-origin iframes by viewport visibility, the Bandcamp embed itself gets cheaper when scrolled away — but it keeps *playing audio*, which is the correct behaviour and another reminder that the embed's lifecycle is independent of yours.

### Gaps
- I did not find a benchmark quantifying canvas-2D-vs-WebGL throughput on specific mobile hardware in this pass, so the element-count thresholds above are engineering judgement, not measured figures.

## Accessibility: WCAG thresholds, reduced motion, photosensitivity, pause controls

### Takeaway
Flashing above three per second is a hard stop; WCAG 2.3.1 (Level A) allows flashing only below the general-flash and red-flash thresholds or within a small area, and 2.3.2 (Level AAA) bans it outright at any size or brightness. A continuously animating visualiser that starts automatically and sits alongside other content needs a pause/stop/hide mechanism under 2.2.2. The defensible design is: no autostart, an explicit play gate carrying a photosensitivity notice, a persistent pause control, and a `prefers-reduced-motion` path that renders a static or near-static frame.

### Cited Findings (quoted)
- **SC 2.3.1 Three Flashes or Below Threshold (Level A)**: "Web pages do not contain anything that flashes more than three times in any one second period," "or the flash is below the general flash and red flash thresholds." — [W3C Understanding SC 2.3.1](https://www.w3.org/WAI/WCAG22/Understanding/three-flashes-or-below-threshold.html)
- **General flash and red flash thresholds** — content passes if "there are no more than three general flashes and / or no more than three red flashes within any one-second period," or if "the combined area of flashes occurring concurrently occupies no more than a total of .006 steradians within any 10 degree visual field," which is "(25% of any 10 degree visual field on the screen) at typical viewing distance." — [W3C Understanding SC 2.3.1](https://www.w3.org/WAI/WCAG22/Understanding/three-flashes-or-below-threshold.html)
- **Flash**: "a pair of opposing changes in relative luminance that can cause seizures in some people," applicable "if it is large enough and in the right frequency range." — [W3C Understanding SC 2.3.1](https://www.w3.org/WAI/WCAG22/Understanding/three-flashes-or-below-threshold.html)
- **General flash**: "a pair of opposing changes in relative luminance of 10% or more of the maximum relative luminance (1.0)," "where the relative luminance of the darker image is below 0.80." — [W3C Understanding SC 2.3.1](https://www.w3.org/WAI/WCAG22/Understanding/three-flashes-or-below-threshold.html)
- **Red flash**: "any pair of opposing transitions involving a saturated red." — [W3C Understanding SC 2.3.1](https://www.w3.org/WAI/WCAG22/Understanding/three-flashes-or-below-threshold.html)
- **Relative luminance**: "the relative brightness of any point in a colorspace, normalized to 0 for darkest black and 1 for lightest white." — [W3C Understanding SC 2.3.1](https://www.w3.org/WAI/WCAG22/Understanding/three-flashes-or-below-threshold.html)
- **The pixel estimate**: "using a 341 x 256 pixel rectangle anywhere on the displayed screen area when the content is viewed at 1024 x 768 pixels will provide a good estimate of a 10 degree visual field"; the Understanding document also states that the 341 x 256 CSS pixel block equals "a flashing area of 87,296 CSS pixels" — [W3C Understanding SC 2.3.1](https://www.w3.org/WAI/WCAG22/Understanding/three-flashes-or-below-threshold.html)
- **No tooling needed below 3 Hz**: "no tool is necessary to evaluate for this condition if flashing is less than or equal to 3 flashes in any one second." — [W3C Understanding SC 2.3.1](https://www.w3.org/WAI/WCAG22/Understanding/three-flashes-or-below-threshold.html)
- **Fine-pattern exception**: "Flashing that is a fine, balanced, pattern such as white noise or an alternating checkerboard pattern" "does not violate the thresholds." — [W3C Understanding SC 2.3.1](https://www.w3.org/WAI/WCAG22/Understanding/three-flashes-or-below-threshold.html)
- **SC 2.3.2 Three Flashes (Level AAA)**: "Web pages do not contain anything that flashes more than three times in any one second period." Unlike 2.3.1 there is no brightness or area escape hatch — 2.3.1 "permits flashing if it is dim enough or covers a small enough area," whereas 2.3.2 "prohibits any flashing above three times per second, regardless of brightness or size, so even a single flashing pixel is a violation." — [W3C Understanding SC 2.3.2](https://www.w3.org/WAI/WCAG22/Understanding/three-flashes.html)
- **SC 2.2.2 Pause, Stop, Hide**, first bullet: "For any moving, blinking or scrolling information that (1) starts automatically, (2) lasts more than five seconds," "and (3) is presented in parallel with other content," "there is a mechanism for the user to pause, stop, or hide it" "unless the movement, blinking, or scrolling is part of an activity where it is essential". Second bullet: "For any auto-updating information that (1) starts automatically and (2) is presented in parallel with other content," "there is a mechanism for the user to pause, stop, or hide it or to control the frequency of the update" "unless the auto-updating is part of an activity where it is essential." — [W3C Understanding SC 2.2.2](https://www.w3.org/WAI/WCAG22/Understanding/pause-stop-hide.html)
- **"Essential" is defined narrowly**: "if removed, would fundamentally change the information or functionality of the content," "and information and functionality cannot be achieved in another way that would conform". — [W3C Understanding SC 2.2.2](https://www.w3.org/WAI/WCAG22/Understanding/pause-stop-hide.html)
- **"Starts automatically" includes indirect triggers**: content "is considered to start automatically either when it starts without direct user activation or interaction (such as activating a button), or when it starts as a result of an indirect interaction" — [W3C Understanding SC 2.2.2](https://www.w3.org/WAI/WCAG22/Understanding/pause-stop-hide.html)
- **prefers-reduced-motion values**: `no-preference` "indicates that a user has made no preference known on the device. This keyword value evaluates as false." `reduce` "indicates that a user has enabled the setting on their device for reduced motion. The `reduce` keyword value evaluates as true; therefore, `@media (prefers-reduced-motion)` is equivalent to `@media (prefers-reduced-motion: reduce)`." The setting "conveys to the browser ... that the user prefers an interface that removes, reduces, or replaces motion-based animations"; "scaling or panning large objects can be vestibular motion triggers" — [MDN prefers-reduced-motion](https://developer.mozilla.org/en-US/docs/Web/CSS/@media/prefers-reduced-motion)
- MDN's reduced-motion example replaces a scaling `pulse` animation with an opacity-only `dissolve` animation, described as "a more muted animation that is not a vestibular motion trigger" — i.e. the sanctioned pattern is *substitute*, not merely *disable* — [MDN prefers-reduced-motion](https://developer.mozilla.org/en-US/docs/Web/CSS/@media/prefers-reduced-motion)

### Cited Findings (photosensitivity / seizure guidance)
- MDN's accessibility guide: "According to the W3C, blinking is a distraction problem, whereas flashing refers to content that occurs more than 3 times per second, and which is sufficiently large and bright." — [MDN Web accessibility for seizures and physical reactions](https://developer.mozilla.org/en-US/docs/Web/Accessibility/Guides/Seizure_disorders)
- The frequency danger band: "Generally, flashing lights between the frequencies of five to 30 flashes per second (Hertz) are most likely to trigger seizures. In order to be safe, the consensus recommends that photosensitive individuals should not be exposed to flashes greater than three per second." And: "For some people, however, flashing/blinking can cause symptoms at less than 3 Hz." — [MDN Seizure disorders](https://developer.mozilla.org/en-US/docs/Web/Accessibility/Guides/Seizure_disorders)
- **Epilepsy Foundation of America consensus, as quoted by MDN**: "A flash is a potential hazard if it has luminance ≥20 cd/m2, occurs at a frequency of ≥3 Hz, and occupies a solid visual angle of ≥0.006 steradians (approximately 10% of the central visual field or 25% of screen area at typical viewing distances)." — [MDN Seizure disorders](https://developer.mozilla.org/en-US/docs/Web/Accessibility/Guides/Seizure_disorders)
- Section 508 "prohibits flickering effects with a frequency greater than 3 Hz (flickers per second) and lower than 55 Hz." — [MDN Seizure disorders](https://developer.mozilla.org/en-US/docs/Web/Accessibility/Guides/Seizure_disorders)
- PEAT's area rule as quoted by MDN: "The combined area of flashes occurring concurrently occupies no more than a total of one quarter of any 341 x 256 pixel rectangle anywhere on the displayed screen area when the content is viewed at 1024 by 768 pixels"; "The 341 x 256 pixel block represents a 10 degree viewport at a typical viewing distance"; developer guidance: "limit the size of the flash to an area approximately 341 by 256 pixels or less" — [MDN Seizure disorders](https://developer.mozilla.org/en-US/docs/Web/Accessibility/Guides/Seizure_disorders)
- On red: "People are even more sensitive to red flashing than to other colors, so a special test is provided for saturated red flashing"; "Irrespective of luminance, a transition to or from a saturated red is also considered a risk"; and a warning that #990000 being "websafe" "does *not* mean it is 'safe for not causing seizures'" — [MDN Seizure disorders](https://developer.mozilla.org/en-US/docs/Web/Accessibility/Guides/Seizure_disorders)
- Controls and warnings, quoted: "Don't include animation that a user cannot control." "Give the user the ability to avoid it, turn it off, or render it less harmful." "control access to it by first displaying a warning about the content, and then putting it in a location where the user must opt in to it, such as clicking a button, or ensuring that the link to the page has a distinct and obvious warning." If flashing is unavoidable: "Make sure it has a control on it. Make sure it is turned off when the viewer first encounters it, and that a user must opt-in to see the animation." — [MDN Seizure disorders](https://developer.mozilla.org/en-US/docs/Web/Accessibility/Guides/Seizure_disorders)
- Also: "Give users a heads-up as to what will happen before they click on that link. Describe the animation that is to follow" (per WCAG 3.2.5); "Use parallax effects with caution; if you must use them, ensure the user has a control to turn them off"; "Drop the contrast ratio if three flashes within one second are detected"; "avoid animating your text"; and the suggestion of `<meta name="robots" content="noindex, nofollow" />` or `X-Robots-Tag: noindex` to reduce accidental discovery of hazardous pages — [MDN Seizure disorders](https://developer.mozilla.org/en-US/docs/Web/Accessibility/Guides/Seizure_disorders)
- Reduced-motion implementation detail worth copying: prefer a very short duration over `none`, because "setting `animation-duration` and `transition-duration` properties to a short duration rather than setting them to `animation: none` and `transition: none`, enables a safeguard to prevent issues in any case there is a dependency on the animation to run"; the nuclear CSS is `@media screen and (prefers-reduced-motion: reduce), (update: slow) { * { animation-duration: 0.001ms !important; animation-iteration-count: 1 !important; transition-duration: 0.001ms !important; } }`; and in JS all running animations can be slowed with `document.getAnimations().forEach((a) => { a.playbackRate *= 0.5; });` — [MDN Seizure disorders](https://developer.mozilla.org/en-US/docs/Web/Accessibility/Guides/Seizure_disorders)
- The Epilepsy Foundation's own article "Shedding Light on Photosensitivity" is reported to state the same consensus — no more than three flashes per second, flashing area no greater than 25% of the total screen area, and 5–30 Hz as the most provocative band — [Epilepsy Foundation: Shedding Light on Photosensitivity](https://www.epilepsy.com/stories/shedding-light-photosensitivity-one-epilepsys-most-complex-conditions); consensus paper PDF hosted by the Foundation — [Epilepsia 46(9):1423–1425, 2005](https://www.epilepsy.com/sites/default/files/atoms/files/Epilepsia%20vol%2046%20issue%209%20Photosensitivity.pdf)
- UK Epilepsy Action notes a wider sensitivity range than the 3 Hz rule implies: "some people can be sensitive to lights that flash as slow as 3 times a second or as fast as 60 times per second" — [Epilepsy Action: Photosensitive epilepsy and online content](https://www.epilepsy.org.uk/press/photosensitive-epilepsy-and-online-content)
- A 2025 review of international photosensitive-epilepsy guidelines (gap analysis and recommendations) exists for anyone wanting the current clinical literature rather than the 2005 consensus — [International Guidelines for Photosensitive Epilepsy: Gap Analysis and Recommendations (PMC)](https://pmc.ncbi.nlm.nih.gov/articles/PMC11872230/)

### Inferences — implementation rules for this site
- **Does the visualiser need a pause control under 2.2.2?** Read the criterion's three conditions against this design. If the visualiser (1) starts automatically — and note that WCAG counts a start "as a result of an indirect interaction", so starting it as a side-effect of the page's play button likely still counts as automatic — (2) lasts more than five seconds, and (3) is "presented in parallel with other content" (i.e. there is text, links, a tracklist or the Bandcamp embed on the same page), then **yes, you must provide a mechanism to pause, stop or hide it**. The "essential" exemption is defined too narrowly to apply: decorative visuals behind an album page can be removed without fundamentally changing the information or functionality. The one configuration that escapes the criterion is a visualiser on a page with *no other content* — a dedicated full-screen "visualiser" route — but that is a weaker product than a pause button.
- **Concrete, quotable implementation rules** (derived from the quotes above, not invented):
  1. Never exceed **3 flashes in any one second** anywhere in the visuals. Below that, no analysis tool is needed at all (2.3.1's own note). This is the single rule that makes everything else moot — adopt it as a hard invariant and you satisfy both 2.3.1 (Level A) and 2.3.2 (Level AAA).
  2. A "flash" requires a **pair of opposing luminance changes of ≥10% of maximum relative luminance, with the darker image below 0.80 relative luminance**. So high-frequency motion within a *narrow* luminance band (e.g. mid-greys shifting by <10% L, or bright-on-bright) is not a flash by definition. Design the palette to live in a ≤10% luminance window if you want fast motion.
  3. **No saturated red transitions at all**, at any rate — the red-flash test is independent of luminance. Avoid pure/near-pure reds for anything that changes rapidly; MDN's #990000 warning shows that "dark red" is not a get-out.
  4. If you must exceed the thresholds, keep the flashing area **below a 341 × 256 px rectangle (87,296 CSS px)**, and more precisely below one quarter of any such rectangle. A full-bleed background visual can never qualify for this exemption — only a small inline widget can.
  5. **Autostart off.** Per MDN's guidance, flashing/animated content should be "turned off when the viewer first encounters it, and that a user must opt-in". This aligns with the autoplay gate you need anyway.
  6. **Warn before entry**, with a specific description rather than a generic "flashing lights" label — "Describe the animation that is to follow". For a music site, a line like "This page shows a moving visual that pulses with the music; it stays below three flashes per second and can be turned off" is both the warning and the reassurance.
  7. **Persistent, keyboard-reachable pause/stop control**, visible without hovering, available at all times (not just in a settings panel), and remembered (localStorage) so a returning visitor isn't re-exposed.
- **The right `prefers-reduced-motion` fallback for an audio visualiser**, in order of quality:
  - Best: **substitute, don't delete**. Follow MDN's dissolve-instead-of-pulse precedent — keep a visual that responds to the music but only through opacity/colour-density changes with heavy smoothing (`smoothingTimeConstant` ~0.9), no translation, no scaling, no camera motion, under 3 Hz by construction. The viewer still gets the connection to the audio; they don't get vestibular motion.
  - Good: **a static frame** rendered from a one-shot analysis (e.g. a single spectrum snapshot, or an album-art-derived still) so the layout doesn't collapse and the page still looks designed.
  - Acceptable: **off by default with an explicit opt-in button** ("Show the animated visual"). This is the honest minimum and is also what the seizure guidance asks for independently.
  - Avoid: silently rendering nothing, which leaves a dead rectangle, and avoid a slow fade/crossfade of *large* objects, since "scaling or panning large objects can be vestibular motion triggers".
- **Honour the preference in both CSS and JS**, because the canvas is drawn in JS and CSS cannot reach it:
  ```js
  const mq = window.matchMedia("(prefers-reduced-motion: reduce)");
  function applyMotionPref() {
    reduced = mq.matches;           // pick render mode
    if (reduced) renderStaticFrame(); else startLoop();
  }
  mq.addEventListener("change", applyMotionPref);  // respond to live OS changes
  applyMotionPref();
  ```
  MDN's prefers-reduced-motion page documents only CSS, so the `matchMedia` form above is the standard JS equivalent rather than a quote. Note that `matchMedia(...).matches` being false means either `no-preference` or an unsupporting browser — treat "unknown" as "no preference" but keep the manual off switch for both.
- **Three independent switches should exist and compose**: the OS preference (`prefers-reduced-motion`), the user's explicit on-page control (WCAG 2.2.2), and the automatic pause when hidden/offscreen (performance). Any one of them being "off" should stop the loop.
- **An audit habit**: the three-flashes rule is easy to violate accidentally through *clearing* behaviour. A visualiser that fully clears to black each frame and then draws bright shapes is, at 60 fps, producing large opposing luminance changes many times per second — if the shapes cover a large area and the coverage varies with the beat, that is a flash sequence even though no code says "flash". Mitigation: use a translucent clear (trails) so luminance changes are gradual, cap the per-frame luminance delta, and clamp overall brightness response so a loud transient cannot swing the whole canvas from near-black to near-white.

### Gaps
- The W3C Understanding page for 2.2.2 does **not** contain two notes specifically about user-launched content (I checked; its four notes cover flashing content, non-interference, streamed/periodically-updated content, and preload animations). If the brief expected such notes, they are not there — the relevant material is the "starts automatically" explanation quoted above.
- I did not fetch the Epilepsy Foundation's and Epilepsy Society's own guidance pages directly; the Foundation's consensus figures above are reported via MDN (which quotes the EFA consensus verbatim) and via a search summary of the Foundation's article. The 2005 Epilepsia consensus PDF hosted on epilepsy.com is the primary document and is linked above for direct verification.
- The 341 × 256 figure is defined "when the content is viewed at 1024 x 768 pixels". No source I read updates this for modern high-DPI phones; MDN only notes that for VR/ocular masks the rectangle should be "much smaller". Treat the pixel rule as a rough proxy and prefer the 3 Hz rule as the operative constraint.

### Inferences
- **The honest pattern across the famous names**: when a major artist wanted a reactive, sensor-driven or generative experience (Massive Attack *Fantom*, Radiohead *PolyFauna*, Eno *Bloom*, Aphex Twin's AR), they shipped an **app**, not a web page — because the era's mobile browsers couldn't do it and because the artwork wanted device sensors. The *websites* in this genre are mostly agency-built album microsites (Audiograph, Bon Iver "i", the Coala Music site). Useful corollary for the brief: there is no established convention that a musician's homepage must be audio-reactive; doing it is a differentiator, not catching up.
- **The two examples actually worth studying**, because they are documented at the code level: `mattdesl/audiograph.xyz` (open source, Three.js + post-processing + `web-audio-player`, shipped as a real album site in 2016 and awarded) and `ryanachten/IndiOfficial` (open source, Canvas 2D + Web Audio FFT, generative Chladni/Lissajous forms on a working artist site). The second is the closer match to a vanilla no-build canvas target. The ARKx/Codrops article is the best *tutorial-grade* write-up but is Three.js-based and its page blocks automated fetching.
- **Why Audiograph worked**: it treated the album as the subject rather than the decoration — one coherent visual world per record, entered deliberately, with the audio loaded and owned by the page (hence `web-audio-player`, hence no embed). That is precisely the architecture this brief needs: *the page owns the audio it visualises*. The Bandcamp embed cannot be that audio; the site's own synthesis or its own files must be.
- **Why the fan-made webVJ pieces and Awwwards one-offs are weaker models**: they are destinations in their own right with no commerce, tracklist, or text alongside — which also means they dodge WCAG 2.2.2's "in parallel with other content" condition. A musician's actual site has to carry links, a tracklist and a buy button, so it inherits the pause-control obligation that a pure visualiser demo does not.
- **Effort calibration**: Nekologic's four person-months for a bespoke shader-based audio-reactive visualiser is the upper bound of this genre. A canvas-2D spectrum/waveform piece with a DPR cap, reduced-motion path and pause control is a day or two. The gap between those two numbers is almost entirely shader authoring and art direction, not Web Audio plumbing — the plumbing is the small part.

### Gaps
- Codrops blocked automated fetching (HTTP 403) and Awwwards returned 503, so the Coala Music technical details and the full Awwwards collection listings come from search summaries rather than direct reads. Verify by visiting both directly.
- I found **no** documented case of a musician's site reacting to an embedded third-party player (Bandcamp, Spotify, SoundCloud) — consistent with the technical impossibility established above, but worth stating as an absence of counter-evidence rather than proof.
- I found no well-documented web prior art for Björk, Nicolas Jaar's sites, 100 gecs / hyperpop-era sites, or Y2K-revival / Yume-Nikki-ish net-art band pages in this pass. These may exist; they are not documented in the sources I reached.

## Validating or challenging the stated plan

### Takeaway
The plan — Bandcamp embed for real playback, Strudel/in-browser synthesis as the analysed signal — is correct, and the evidence above says it is the *only* workable architecture of its kind. The challenge is not technical but editorial: the visuals will be reacting to something other than the music the visitor is listening to, and the design has to be honest about that.

### Cited Findings
- The embed cannot be analysed: Bandcamp's API is limited to Account / Sales Report / Merch Orders for "labels and merchandise fulfillment partners" — [Bandcamp developer](https://bandcamp.com/developer); the embedded player exposes no JS/playback API — [Parachord issue #1231](https://github.com/Parachord/parachord/issues/1231); and cross-origin media routed into Web Audio outputs silence — [Mozilla bug 937718](https://bugzilla.mozilla.org/show_bug.cgi?id=937718)
- Strudel's own output context is reachable (`getAudioContext`, `webaudioOutput`) and it ships a click-to-unlock helper (`initAudioOnFirstClick`) — [@strudel/webaudio README](https://app.unpkg.com/@strudel/webaudio@1.1.0/files/README.md)
- Strudel already has an analyser mechanism (`.analyze(id)` + `fft(n)`, with `tscope`/`scope.mjs` as reference) — [Tidal Club thread](https://club.tidalcycles.org/t/strudel-audio-reactive-get-values-from-audio-output/5413)
- Netlify-hosted own files are same-origin, so the `crossOrigin` + `Access-Control-Allow-Origin` requirement that bites cross-origin audio simply does not arise — the requirement is specifically for cross-origin resources — [wavesurfer.js issue #2014](https://github.com/katspaugh/wavesurfer.js/issues/2014)

### Inferences
- **Validated**: Strudel-as-signal is the right call. It gives a perfect analyser tap, zero bandwidth, zero CORS surface, no licensing question, and it is genuinely generative rather than a loop — which suits a "Sane Asylum Presents" compilation page better than a canned spectrum would. It also solves the autoplay problem cleanly because Strudel already requires and provides a first-click unlock.
- **Two audio sources, one pair of ears.** The real risk is a visitor pressing play on the Bandcamp embed *and* starting the Strudel layer, hearing both at once. You cannot detect the embed's state, so you cannot auto-duck. Mitigations, in order of preference: (a) make the two mutually exclusive in the UI — the Strudel layer is an "intro / idle" mode and the visible act of pressing play on the album replaces it, with a clear single "now playing" indicator; (b) put the Strudel visualiser on its own route/section away from the embed; (c) keep the Strudel layer silent by default and let the visuals be driven by it as an inaudible generative clock, so visuals move with *something* musical without competing with the album. Option (c) is worth serious consideration: an analyser on a muted-but-running synth graph (connect the synth to the analyser only, not to `ctx.destination`) gives you a real, structured, tempo-locked signal with no sound at all and no autoplay gesture problem for the audio part — though you still need a gesture to start the AudioContext.
- **Consider the hybrid**: a short self-hosted preview (one 60–90 s excerpt) as the *default* visualiser source, so first-time visitors see the visuals respond to the actual record; the Bandcamp embed for full playback and purchase; Strudel as an optional "play with it" mode. Same-origin files on Netlify make the preview trivial, and a 90-second Opus excerpt is under ~1.5 MB.
- **Don't oversell it.** Avoid copy implying the visuals read the album stream. A label like "generative visual — press play on the album below to listen" is accurate and avoids the uncanny mismatch a visitor notices within seconds when the bars don't match the beat.
